Reference

The thirteen skills and their commands, the terms the method uses, the questions people ask first, and where the rules are written down.

#Skills

Install all thirteen with npx skills add mpurbo/hsdd. Each one is a SKILL.md an agent loads when your request matches it; you can also name it in the prompt.

#Build the tree

hsdd-spec

Build the tree/hsdd-spec

Turn a brain-dump into a high-level spec, or decompose any node into child nodes. Recursive: runs at the root and every internal level.

Interactive guide: DecomposeSKILL.md on GitHub

hsdd-contract

Build the tree/hsdd-contract

Define and version the first-class contracts between nodes.

Interactive guide: ContractsSKILL.md on GitHub

hsdd-adr

Build the tree/hsdd-adr

Author and maintain cross-cutting Architecture Decision Records as first-class files, with registry-compatible frontmatter and a status lifecycle.

Interactive guide: ContractsSKILL.md on GitHub

#Plan the phases

hsdd-phase-plan

Plan the phases/hsdd-phase-plan

Break a small-enough node into ordered, independently implementable phases, each sized for one coding cycle and one review window.

Interactive guide: Plan phasesSKILL.md on GitHub

hsdd-reconcile

Plan the phases/hsdd-reconcile

Drain the pending governance updates emitted by phase planning: finalize contract phase ids, resolve contract-gap requests with you, and regenerate the registries. Runs on the root lineage after parallel plan branches merge.

Interactive guide: Plan phasesSKILL.md on GitHub

#Execute a phase

hsdd-config

Execute a phase/hsdd-phase

Before each phase, write one self-contained phase context (the phase, the text of the contracts it touches, its decisions, pinned links) and wrap it for the project's coding method: OpenSpec's config.yaml, or a spec for superpowers' writing-plans.

Interactive guide: Execute a phaseSKILL.md on GitHub

#Existing systems and change

hsdd-adopt

Existing systems and change/hsdd-adopt

Bring an existing codebase into the tree: script-extracted seams, as-built node specs with an ## Observed surface section, and v0 contracts describing current behavior. Brownfield's entry point.

Interactive guide: Adopt a codebaseSKILL.md on GitHub

hsdd-intake

Existing systems and change/hsdd-intake

Route an incoming change request (PRD, RFC, ticket, incident) into the existing tree: classify it, detect collisions with open intakes, write the routing record, and hand off. A PRD is never a root.

Interactive guide: Route every changeSKILL.md on GitHub

hsdd-seal

Existing systems and change/hsdd-seal

Seal a released tree whose artifacts went stale, by script and with no model in the loop: a plan with a default class per phase, the owner's edit of that class, then retroactive verification docs by delegated sign-off, Status: dropped on unbuilt phases, pruned catch-up OpenSpec directories, closed intake records and the campaign document sealed into the archive.

Interactive guide: Route every changeSKILL.md on GitHub

#Run the project

hsdd-checkpoint

Run the project/hsdd-checkpoint

Run the weekly (or context-triggered) evidence pass across the spec repo and every implementation repo, emitting a progress report, a revised execution plan, a regenerated atlas, and ticked milestone gates. One pass, four views; every finding becomes a plan step or an explicit waiver.

Interactive guide: Evidence and milestonesSKILL.md on GitHub

hsdd-milestone

Run the project/hsdd-milestone

Generate a campaign's stakeholder milestone document once every leaf-parent in its scope is phase-planned. Each checkpoint is a demo and a gate; externally-gated work sits in a contingent tail outside the launch gate. Re-baseline the document when the dates move.

Interactive guide: Evidence and milestonesSKILL.md on GitHub

hsdd-summary

Run the project/hsdd-summary

Render offline HTML reading aids: the plan page (root to phase cards, for a reviewer, a stakeholder or an implementer) and the checkpoint page (the newest progress report and execution plan, for the lead running the sync, each lane's executor, and stakeholders).

Interactive guide: Evidence and milestonesSKILL.md on GitHub

#Unattended

hsdd-auto

Unattended/hsdd-auto

Run HSDD's planning chain unattended: compute the next step, dispatch one fresh subagent per skill invocation, answer or stop on each ask point per the owner's stop policy, gate and commit each step, and record every decision for one review sitting.

Interactive guide: Run unattendedSKILL.md on GitHub

#Glossary

The interactive guide's glossary, the same entries it opens with G. The specification's last chapter is the full glossary.

Node
Any unit in the spec tree. Every node has the same header at every level: kind, purpose, owning team, what it owns and does not own, the contracts it consumes and produces, its sources, and how to test it in isolation.
Internal node
A node that splits into child nodes. The system, a domain such as the backend, and a subsystem are all internal nodes.
Leaf-parent
A node whose children are phases rather than more nodes. One owner can hold its whole scope in their head, and it owns a phase plan.
Phase
The smallest independently verifiable unit of work. One phase drives exactly one coding cycle and ends at one human review gate. Its id is its leaf-parent's id plus a number, such as acme.backend.auth.2.
Phase Equivalent (PE)
The sizing unit: the largest change one reviewer can genuinely review and manually verify in one sitting, plus the agent run that produced it. Roughly 400 changed lines of non-generated code, at most 8 tasks, about half a working day.
Contract
A named, versioned interface between nodes: an API, an event, a schema, a shared type, a file layout, or a CLI. It is the only thing one node may know about another. Written as id@version, such as auth-token@v1.
Dependency type
Every edge between nodes is typed. hard: needs the producer's real output. contract: builds against fixtures. event: builds against the event schema. shared-model: needs the shared type. Only hard edges make a consumer wait for the producer to ship; the others need only a stable contract or the shared type.
Stable contract
A contract with at least one executable validation artifact, a schema or a fixtures directory. The producer's gate replays it and consumers test against the same fixtures.
Registry
The INDEX.md files for contracts and ADRs. A script generates them from frontmatter; nobody, human or agent, edits them by hand.
ADR
Architecture Decision Record: a cross-cutting, durable decision kept as its own file, such as hsdd/adr/001-auth-provider.md, so the registry and phase contexts can find it by id. A decision inside one node stays a D{n} in that node's spec.
Open question (OQ)
A decision that cannot be made yet. It is defined once, in the spec that owns it (OQ3 at the root, OQ-B3 in a node), and cited everywhere else by id. Phases that wait on it are marked contingent.
Sources
The input documents (PRD, RFC, design, ticket) that govern a node. Sources trickle down at every split, so a later step reads the original rather than a summary of a summary.
Review tier
How much human attention a phase gets at its gate, set by risk: gate-only, spot-check, or full-review. The tier also sets how many artifacts the coding cycle writes.
Governance freeze
During phase planning, contracts, ADRs, conventions.md and the registries are read-only, at the root and in every worktree. Planners write the changes they need into their own plan file, as data.
Reconcile
hsdd-reconcile, the single writer for governance. At the root it applies the pending updates that phase plans emitted (confirm, request, amend, note), resolves requests with you, flips contracts to stable, and regenerates the registries.
Phase context
The self-contained file /hsdd-phase writes before a phase runs: the phase, the Interface, Guarantees and Validation of its contracts, its decisions, the discipline, and links pinned to a spec commit. It is then wrapped for OpenSpec or superpowers.
Coding method
How a project runs each phase's coding cycle: openspec or superpowers. HSDD decides what each cycle sees and in what order cycles run; the cycle itself is unchanged.
Verification doc
hsdd/verify/{phase-id}.verification.md: commands, expected and observed output, outstanding items, learnings, and the human sign-off. Merged to main, it is the only admissible proof that a phase is done.
Learning
A finding at the gate about the tree rather than the phase. Each one gets a disposition before sign-off: spec-updated, contract-bumped, adr-proposed, or dropped. Writing none is fine; leaving it blank is not.
Integration node
A leaf-parent whose phases exercise the real composed behavior of sibling nodes. Its hard edges to each producer schedule it after they ship.
Seams
The places where a system's parts meet that tooling can see without reading the code: manifests, route registrations, schemas, migrations, event topics, CODEOWNERS, and files that change together in git history.
As-built node
An adopted node whose spec records observed structure, marked Adopted: as-built. It stays that way until a change lands on it, and some nodes stay that way for good.
Promoted node
An as-built node that a change landed on, decomposed under governance after a human confirmed it. Marked Adopted: promoted. Its observed surface stays as provenance.
Observed surface
The section of an as-built spec holding only what the seam extractor saw (modules, routes, tables, topics, owners), stamped with the commit it looked at, plus the required unknown: lines a human adds.
v0
The version of an adopted contract: observed behavior, warts included. It is permanent. A contract moves to v1 only when its interface is genuinely redesigned.
Observed completeness
The required section of a v0 contract that names what its fixtures do not reach.
Intake record
The dated record hsdd-intake writes for each change request before any handoff: class, landing nodes, contracts, promotions, collisions, routing. Never superseded; records accumulate, one per request.
Backfill
The finding filed when code ships with no phase, such as a hotfix. It becomes a retro phase with a verification doc marked retroactive.
Checkpoint
hsdd-checkpoint: one evidence pass over the spec repo and every implementation repo, usually weekly, producing a progress report, an execution plan, the atlas, and ticked milestone gates.
Atlas
hsdd/management/atlas.md: a regenerated bird's-eye view of the tree with phase status, the contract graph, and ADR coverage. Derived only; if it disagrees with the artifacts, the atlas is wrong.
Milestone
A stakeholder checkpoint: a demo someone can watch work, plus a gate of yes/no checkboxes. Work that waits on outside parties goes to a contingent tail outside the launch gate.
Reading aid
An optional offline HTML page rendered by hsdd-summary over the canonical files: the plan page for reviewers and the checkpoint page for the weekly sync. Derived, never edited.
Run and segment
An unattended run is one hsdd-auto effort on one branch, configured by hsdd/auto/run.yaml. A segment is one stretch of it, opened by one owner instruction (the first /hsdd-auto, an intake, or an answer to STOP.md), with one mode, one stop policy and one report.
Orchestrator
The agent session that runs hsdd-auto. It launches one fresh subagent per step, answers stops as the owner's stand-in or ends the run, reviews each step, and runs the scripts that gate, commit and record. It never runs a planning skill in its own context.
Decision ledger
hsdd/judgement/decisions.jsonl: one decision per line, append-only. Each line holds the question, the options and their consequences, the choice, why, the evidence, the blast radius and the confidence, pinned to the commit that holds the artifact it landed in.
Stop policy
Chosen per segment. stop: a condition in the stop set (axis, shape, promotion, breaking-amend, collision, external, gate-twice) ends the run with STOP.md. decide-and-record: the run decides it and records the decision with would_have_asked: true. Hard stops, such as a need outside the repository, end the run under either policy.
would_have_asked
A decision field: true when a skill stopped for a human, or a careful engineer would have asked the owner first. The segment report lists these decisions first.
Predecided answer
The answer to a stop class, decided once before any step meets it and carried in every later prompt. A subagent that meets the class applies it, records its own decision citing it, and does not stop.

#Common questions

Does HSDD replace OpenSpec or superpowers?

No. HSDD wraps a decomposition front-end and a contract layer around the coding cycle you already use. It decides what each cycle sees and in what order cycles run. Each phase is one ordinary OpenSpec change or one superpowers plan.

Will it cut my token bill?

It bounds each session's context to one phase plus the contracts and decisions it touches. Total tokens across a project still grow with the number of phases, and planning has its own overhead. HSDD bounds the cost per session; it does not reduce the total.

Does context isolation stop an agent from reading other files?

No. Isolation shapes attention: a session that only received its own phase is unlikely to wander into a sibling's concern or invent an interface it was never given. That held up under adversarial testing, but it is probabilistic, not enforced by a mechanism.

Do I need a deep tree for a small project?

No. When the system is one coherent responsibility, the root is a leaf-parent and you go straight to phases, as in the linkcheck example. Depth and ceremony are costs: use as many levels and artifacts as the system needs and no more.

Why split by team rather than by feature?

A node owned by two teams mixes two toolchains and two deploy targets and has no single owner, so nobody can hold its scope. Split where ownership splits; a feature that spans the stack comes back one level down as a pair of nodes joined by a contract. A solo developer or one full-stack squad can slice by feature, because there the feature boundary is the ownership boundary.

How big is a phase?

One Phase Equivalent: what one reviewer can genuinely review and manually verify in one sitting, plus the agent run. Roughly 400 changed lines of non-generated code, at most 8 tasks, about half a working day. Bigger gets split; a phase too small to earn its own cycle gets merged with a neighbor.

What if a contract turns out wrong in the middle of a phase?

Pause at a task boundary and write the gap into the verification doc's Outstanding section. Renegotiate it at the root through hsdd-contract, bring the change into the phase's branch, re-run the phase switch, and resume. The agent never improvises around the contract.

Can I use HSDD on an existing codebase?

Yes. hsdd-adopt extracts the seams by script, proposes a shallow tree for you to confirm, writes as-built node specs and v0 contracts, and stops. Every change then enters through hsdd-intake, and a node is decomposed further only when a change lands on it.

Why not reverse-engineer the whole codebase into specs?

Cost and trust. Shallow adoption reads structure, not code, so its cost scales with the number of seams rather than lines of code. And nobody reads 500 generated specs, yet every later agent session would treat them as authoritative. HSDD writes a node's spec when someone is about to work on that node and confirms it.

What about hotfixes that skip the process?

Ship the fix. The next checkpoint finds code that no phase covers and files a backfill finding; a retro phase with a retroactive verification doc closes it. A backfill left open for two checkpoints in a row escalates. A recorded bypass beats a hidden one.

What does done mean?

A phase is done when its verification doc, signed by a human, is merged to the spec repo's main branch. Progress reports list anything else as a claim, not as done.

Our backend and frontend live in separate repos.

Use the standalone-spec-repo profile. The tree lives in its own repo, mounted as a git submodule at hsdd/ in each implementation repo, so every path stays the same. Skills run from an implementation repo, where the code they reason about is present.

Is there a CLI or a server to run?

No. HSDD is a set of agent skills with optional slash commands. Scripts exist only where a skill bundles them: the registry generator, the seam extractor, the reading-aid renderer, and hsdd-auto's run scripts. Nothing starts a run on a timer.

Can an agent plan the whole tree without me?

Yes, with hsdd-auto. It runs the planning skills one fresh subagent at a time, gates and commits every step, and records every decision with its options and evidence. You choose per segment whether a stop condition ends the run or is decided and recorded. Your review moves from each question to one sitting over the decisions. It never implements a phase or passes a review gate.

How proven is it?

The core model was field-tested on a production monorepo (14 planned phases across two nodes) and held up in an adversarial pressure campaign. Most of the newer brownfield and steady-state rules are reasoned rather than field-tested, and the spec's decision table marks which is which. hsdd-auto packages a protocol that one field test ran by hand; its stop path has not been exercised in the field. A published end-to-end case study with a baseline comparison is the v1.0 release criterion.
