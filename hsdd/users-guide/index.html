User's guide

HSDD User's Guide

Source: docs/users-guide.md on GitHub

This guide shows HSDD on three worked examples, then covers running a project week to week. Each example goes prompt by prompt: what you type, which skill answers, and the files it writes. The rules behind every step are in the methodology specification, the single current spec, with the v0.11 delta for unattended runs; the superseded delta series remains in spec/ as history. The interactive guide draws the same examples step by step, and the tutorials are complete recorded runs on a real repository.

#Before you start

Install the thirteen skills (see the README) and, ideally, Obra's superpowers plugin. HSDD composes with its test-driven development, verification and code-review skills instead of re-implementing them. The HSDD loop, in one line:

decompose -> contract -> phase-plan (parallel across leaf-parents) -> reconcile -> configure -> one coding cycle per phase (OpenSpec or superpowers) -> human review -> repeat.

One principle is worth taking in early: depth and ceremony are costs. Use exactly as many levels and artifacts as the system needs, and no more. In Example 1 the root is its own leaf-parent; Example 2 needs two levels of nodes under its root. Each is right for its system.

#Plain OpenSpec vs HSDD

Plain OpenSpec drives the whole system from one spec through one cycle, so every session carries the entire spec as context. HSDD decomposes the system into a tree of nodes coupled by versioned contracts, then runs one isolated OpenSpec cycle per leaf phase. Each cycle sees only its phase plus the contract interfaces it consumes.

The OpenSpec cycle itself is unchanged. HSDD only decides what each cycle sees and in what order cycles run. The same holds for superpowers, the other coding method: HSDD writes the phase context, and the method's own skills plan and build the phase (Example 2, Step 5).

#The HSDD workflow

The one-line loop above, drawn out. Planning is done once per node and rarely rewritten. Execution repeats once per phase: switch the context, run the cycle, generate the verification doc, and pass a human review gate before moving on.

The single amber node is the human review gate. Every leaf phase ends there, at a depth set by its review tier (gate-only, spot-check, or full-review).

#Review tiers

hsdd-phase-plan assigns one tier per phase, based on risk rather than size. The tier sets how much attention the gate gets and the artifact profile of the cycle: a gate-only phase skips design.md and gets a slim verification doc; a spot-check phase skips design.md unless the phase settles a real design decision, and gets a short verification doc; a full-review phase produces the full set. Every phase still ends at the gate and still produces a verification doc. Only the depth scales with the tier.

  • gate-only is for scaffolding, types and boilerplate. A wrong turn here is cheap and mechanical to catch, so the automated gate (e.g. cargo test) passing is enough: you're notified and move on without reading the diff. Examples: linkcheck.1 and acme.backend.auth.1, both "Types + contract" phases with no logic yet to get wrong.
  • spot-check is for well-constrained phases with a clear contract, where the output's shape is easy to eyeball without tracing every line. Glance at the diff, confirm the gate passed, proceed. Examples: linkcheck.2, a pure HTML -> [Url] extractor, and acme.backend.auth.3, the session store, both narrow, single-purpose and easy to sanity-check at a glance.
  • full-review is for orchestration, business logic, integrations and security, where mistakes are expensive and not obviously visible in a diff. Read the diff, run the manual verification steps from the phase's verification doc, and think through edge cases before approving. Examples: linkcheck.3, the HTTP checker with retries and timeouts, and acme.backend.auth.2, token issuance, whose manual verification runs before sign-off in Step 6 of Example 2.

See the methodology spec, chapter 7 for how the tier interacts with the review sitting and the sizing floor, and chapter 10 for the tier-scaled artifact profile.

#Where everything lives

Every HSDD artifact lives under one root directory, hsdd/, with singular directory names; only OpenSpec's own files and the per-phase contexts stay outside it. This is the default layout the skills emit (override it in hsdd/conventions.md; spec §14.1 has the full tree):

text
hsdd/conventions.md                        naming, layout, and process conventions
hsdd/spec/{node-id}.md                     node specs and phase plans
hsdd/verify/{phase-id}.verification.md     per-phase verification docs
hsdd/contract/{slug}.md + INDEX.md         first-class contracts (registry generated)
hsdd/contract/schema/, hsdd/contract/fixture/  executable validation; a contract is stable only with one of these
hsdd/adr/{nnn}-{title}.md + INDEX.md       cross-cutting decisions (hsdd-adr, registry generated)
hsdd/scripts/gen-registry.mjs              registry generator (copied from hsdd-contract)
hsdd/scripts/seams/                        seam extractor (copied from hsdd-adopt; adopted trees only)
hsdd/scripts/summary/                      hsdd-summary's scripts (copied verbatim)
hsdd/scripts/auto/                         hsdd-auto's scripts (copied by its first setup step; unattended runs only)
hsdd/templates/verification.md             verification-doc template, copied from hsdd-config
hsdd/management/                           management layer (progress reports, execution plans, milestones, intake records, atlas), written only by hsdd-checkpoint, hsdd-milestone and hsdd-intake (intake records)
hsdd/management/archive/                   sealed milestone documents (closed campaigns)
hsdd/summary/                              optional reading aids (hsdd-summary): summary.html, checkpoint.html
hsdd/auto/, hsdd/judgement/                an unattended run's records and its decision ledger (hsdd-auto)
openspec/                                  config.yaml + one change per phase (OpenSpec method)
hsdd-context/{phase-id}.md                 generic phase context, written by /hsdd-phase before each phase
hsdd-context/superpowers/{phase-id}.md     the same context as a spec for superpowers' writing-plans (superpowers method)

Where to run openspec init: once, at the repo root (the directory that holds hsdd/). One HSDD tree has one OpenSpec project. Every phase, across every node, is a change under that single openspec/changes/; phases are kept apart by the per-phase context switch (hsdd-config), not by separate projects. A project on the superpowers method has no OpenSpec project to initialize.

When the code lives in several repositories, the tree still has one home. The standalone-spec-repo profile keeps one HSDD tree in its own repo, mounted at hsdd/ in each implementation repo, and openspec init runs once per implementation repo. Never give a second repo its own hsdd/spec/; one project has one tree (see Multi-repo projects).

#Example 1: A simple project (single level)

In the interactive guideDecompose Plan phases

Sometimes the whole system is small enough that there is nothing to decompose: the root node is already a leaf-parent, and you go straight to phases. HSDD does not force a tree on you.

The project: linkcheck, a CLI that crawls a site and reports broken links.

#Step 1: Spec it

prompt
You: "Write a high-level spec for linkcheck, a CLI that crawls a site and
      reports broken links."

hsdd-spec runs at the root. It recognizes the project is one coherent responsibility that fits a handful of phases, so it marks the root a leaf-parent rather than inventing sub-nodes. hsdd/spec/linkcheck.md:

markdown
# linkcheck: Broken Link Checker CLI

- **Kind:** leaf-parent
- **Purpose:** crawl a site, check every link, report the broken ones
- **Consumes:** none
- **Produces:** [linkcheck-report@v1]
- **Decomposes into:** phases (see phase plan)
- **Isolation strategy:** pure HTML parsing and pure report formatting are testable
  with fixtures; the HTTP checker is mocked in tests.

For a project this small there is just one outward contract (the report format). The "contracts" between phases are simply the domain types defined in phase 1.

#Step 2: One contract

prompt
You: "Define the linkcheck-report contract."

hsdd-contract writes hsdd/contract/linkcheck-report.md with frontmatter plus the report schema (JSON shape and exit codes), and the contract's executable validation artifact, hsdd/contract/schema/linkcheck-report.schema.json, from that Interface. Then it regenerates the registry:

bash
node hsdd/scripts/gen-registry.mjs

#Step 3: Phase-plan

prompt
You: "Write the phase plan for linkcheck."

hsdd-phase-plan orders the phases by the project's ordering policy (interfaces-first unless hsdd/conventions.md says otherwise), each one PE (<= 8 OpenSpec tasks), opening with the phase summary table:

Phase Name Tier Size Depends on
linkcheck.1 Types + report contract gate-only small -
linkcheck.2 HTML link extractor spot-check small 1
linkcheck.3 HTTP checker full-review medium 1
linkcheck.4 Crawl + report + CLI full-review medium 2, 3

and the dependency graph as a Mermaid flowchart:

Phase 1 produces linkcheck-report@v1, so its Gate includes the contract replay: the phase's real output must validate against the schema hsdd-contract wrote in Step 2, and the contract can only become stable because that artifact exists. Read the schema before you plan on it:

bash
$EDITOR hsdd/contract/schema/linkcheck-report.schema.json   # the JSON shape the report emits

The contract's ## Validation section names that path. A phase never writes it; a schema that turns out wrong is caught by the replay and fixed at the root through hsdd-contract.

The plan ends with a ## Governance updates (pending reconcile) section (confirming the linkcheck-report@v1 phase ids). Even serial, finish planning with a quick reconcile:

prompt
You: "Drain the pending governance updates."

hsdd-reconcile applies the confirms, flips the contract to phase_ids: final and status: stable, and regenerates the registry. With one node this takes a minute; the same step is what makes parallel planning safe in Example 2.

#Step 4: Configure, run, review

prompt
You: "Set up OpenSpec config for this project."
You: "/hsdd-phase linkcheck.1"      (switch context, then run the cycle)
You: "opsx: new ..."                 (proposal -> design -> tasks -> apply -> archive)

At apply, the agent writes hsdd/verify/linkcheck.1.verification.md. Because phase 1 is gate-only, you confirm the gate passed and move on. Phase 3 (the HTTP checker) is full-review: you read the diff and run the manual verification before approving. Repeat for .2, .3, .4.

That is the whole project. No internal nodes, one contract, four phases. The methodology stayed out of the way.

#Example 2: A multi-level system

In the interactive guideDecompose Contracts Plan phases Execute a phase

The project: acme, a full-stack merchant onboarding platform with a backend, a mobile app and a web console, built by separate teams. This one needs the tree.

The root splits by stack because each stack has its own team. That is the decomposition-axis rule (spec §2.5): the axis follows ownership, which is why acme does not decompose into auth-end-to-end / billing-end-to-end slices spanning both stacks.

#Step 1: Decompose the root

prompt
You: "Write a high-level spec for acme, the merchant onboarding platform in
      docs/onboarding-prd.md, with a backend, a mobile app, and a web console."

hsdd-spec splits the root into three internal nodes and names the contracts between them. Because the input is a document, hsdd/spec/acme.md records it in a ## Sources section, and each node it governs carries a - **Sources:** docs/onboarding-prd.md (§...) line. Sources trickle down at every split, so a later phase planner reads the original instead of trusting the summary (spec §2.6). The root spec also includes this typed dependency DAG:

Because the edges are contract, shared-model, and event (not hard), the mobile and web teams can build against mocks as soon as the contracts are stable. They do not wait for the backend implementation.

#Step 2: Recurse into the backend

prompt
You: "Break down @hsdd/spec/acme.backend.md into auth, billing, and catalog subsystems."

hsdd-spec runs again, now for an internal node, producing acme.backend.auth.md, acme.backend.billing.md, acme.backend.catalog.md. The auth node is small enough to phase, so it is marked leaf-parent. If billing were too big, you would recurse once more (insert an internal node) rather than forcing a flat phase split.

#Step 3: Contracts and a decision

prompt
You: "Define the auth-token contract: auth produces it, billing and mobile consume it."

hsdd-contract writes hsdd/contract/auth-token.md (frontmatter + interface + guarantees + v1) and, as in Example 1, its executable validation artifact: hsdd/contract/schema/auth-token.schema.json from the Interface, and example payloads under hsdd/contract/fixture/auth-token/, the fixtures billing and mobile will build against. The choice of auth provider affects more than one node and must outlive the auth subsystem, so hsdd-spec proposes an ADR and hands it to hsdd-adr to materialize:

prompt
You: "Write the ADR for the auth provider decision."

hsdd-adr writes hsdd/adr/001-auth-provider.md. The frontmatter mirrors a contract, so the same generator projects it into hsdd/adr/INDEX.md:

markdown
---
id: ADR-001
status: accepted
affects: [acme.backend.auth, auth-token@v1]
date: 2026-07-02
---

# ADR-001: Auth provider

## Context
Login must work across mobile and web, and key material must rotate.
## Decision
Use provider X with rotating asymmetric keys.
## Consequences
- token verification needs the public JWKS endpoint
- key rotation is a hard dependency for auth.2

It also sets Governed by: [ADR-001] on acme.backend.auth and auth-token@v1, then regenerates the registry (node hsdd/scripts/gen-registry.mjs). The ADR is a file, not a section in the node spec, so hsdd-config can later inject only its Decision and Consequences into the auth.2 phase context.

#Step 5: Configure and switch phase context

prompt
You: "Set up OpenSpec config for this project."
You: "/hsdd-phase acme.backend.auth.2"

The phase switch injects only what auth.2 needs. The OpenSpec session for auth.2 never sees the billing spec, the web spec, or sibling phases:

  <!-- hsdd-phase-context:begin -->

  ## Goal
  Issue JWTs on login via provider X; sign, set claims, handle errors.

  ## Where it sits

  - Owns: login, token issuance, sessions
  - Does not own: merchant profiles, billing

  ## Phase

  - **Scope:** Issue JWTs on login via provider X; sign, set claims, handle errors.
  - **Size estimate:** ~6 files (~400 lines), <= 6 OpenSpec tasks
  - **Gate:** `cargo test` plus contract replay for auth-token
  - **Verification:** a sandbox login returns a token whose claims match auth-token@v1
  - **Review tier:** full-review

  ## Contracts
  ### auth-token@v1 · produces · stable

  A signed JWT with the claims `{ sub, exp, iat, scopes }`.
  **Guarantees**
  - `exp > iat`

  **Validation**
  - schema: hsdd/contract/schema/auth-token.schema.json
  - fixture: hsdd/contract/fixture/auth-token/

  ## Decisions

  **Decision**
  Use provider X with rotating asymmetric keys.
  **Consequences**
  - token verification needs the public JWKS endpoint
  - key rotation is a hard dependency for auth.2

  ## Discipline
  - Test-first: write each behavior's failing test, and see it fail, before
    the code that makes it pass.
  - Governance freeze: change nothing under hsdd/ except this phase's
    verification doc; contracts, ADRs, specs and conventions change only

The same switch writes hsdd-context/acme.backend.auth.2.md first: the method-neutral phase context that the config.yaml block above is copied from, word for word. A team on superpowers instead of OpenSpec runs:

prompt
You: "/hsdd-phase acme.backend.auth.2 --method superpowers"

and starts the phase's session with Use superpowers:writing-plans to plan hsdd-context/superpowers/acme.backend.auth.2.md. #Step 6: Run, verify, parallelize

prompt
You: "opsx: new ..."   (proposal -> design -> tasks -> apply -> archive)

apply writes hsdd/verify/acme.backend.auth.2.verification.md. The phase is full-review, so you read the diff and run its manual verification before you sign. The doc's ## Learnings section carries anything the gate taught you about the tree, each line with a disposition (spec-updated, contract-bumped, adr-proposed, dropped), or - none; the gate is not passed while a line lacks one.

Meanwhile, in a separate session or by another teammate, the web team starts acme.web.dashboard against the auth-token@v1 mock, and billing starts against the same contract. Three teams, three small contexts, one shared contract.

#Step 7: Parallel leaf-parents, worktrees, reconcile

When two leaf-parents are independent (their only edges are contracts), plan them concurrently, one git worktree per node:

bash
git worktree add ../acme-auth plan-auth
git worktree add ../acme-billing plan-billing

Run hsdd-phase-plan in each worktree. Under the governance freeze, neither run edits hsdd/contract/, hsdd/adr/, or hsdd/conventions.md; each emits its intended changes into its own plan file, so the branches touch disjoint files. Billing's section might read:

markdown
## Governance updates (pending reconcile)

> Emitted by hsdd-phase-plan on 2026-07-05. Drained by hsdd-reconcile;
> do not apply by hand.

- confirm `auth-token@v1` consumers: [acme.backend.billing.2]
- request `auth-token@v1`: which fixture do consumers mock against?
  - assumption: `hsdd/contract/fixture/auth-token/`
  - contingent phases: acme.backend.billing.2

Merge both branches (clean by construction), then at the root:

prompt
You: "Reconcile the worktrees."

hsdd-reconcile drains both sections: applies the confirm ids, resolves the fixture request with you, flips auth-token@v1 to phase_ids: final and status: stable, and regenerates the registry. Only then do billing's per-phase OpenSpec cycles start.

#Step 8: Execute phases on branches

Planning worktrees (Step 7) keep governance frozen while node specs are built. Execution has its own branch discipline, one level down. Each node gets one integration branch. The phase branches of acme.backend.auth, acme.backend.auth.1 through .4, merge into integration/acme.backend.auth as each phase's OpenSpec cycle lands; acme.backend.billing's phases merge into their own integration/acme.backend.billing the same way. Node integration branches then merge into the root branch. A node's plan file (hsdd/spec/acme.backend.auth.md) is written on exactly one lineage and is never re-planned or copied onto a diverged sibling lineage. hsdd-reconcile runs once, at the root, after the node's integration branch lands there, never per worktree or per phase.

bash
git checkout -b integration/acme.backend.auth main
git merge acme.backend.auth.1
git merge acme.backend.auth.2
# ... one merge per phase, in dependency order
git checkout main
git merge integration/acme.backend.auth

openspec/config.yaml's ## Current Phase block is rewritten by every /hsdd-phase switch, so a merge conflict on it carries no information: take either side and re-run /hsdd-phase {next-phase} before starting the next cycle. If acme.backend.auth.2 and acme.backend.auth.3 land on integration/acme.backend.auth in either order, do not hand-merge their two Current Phase blocks; pick either one, then switch. Set openspec/config.yaml merge=ours on integration branches in .gitattributes to skip the conflict prompt entirely.

Not every pair of a node's phases parallelizes cleanly. If acme.backend.auth.3 (session store) and acme.backend.auth.4 (auth API + wiring) both touch the same router file, the phase plan says so with - **Collides with:** [acme.backend.auth.4] on .3's section, and the summary table from Step 4 shows the column. Colliding phases execute serially on the node's integration branch; spawn a worktree per phase only where the table shows no collision between them, the same way Step 7 spawned one worktree per non-colliding leaf-parent.

Finally, name the OpenSpec capability each phase's proposal targets after a stable feature area of the node, such as auth-sessions or auth-token-issuance, not after the phase (acme-backend-auth-3). A phase-named capability has nothing left to say once that phase archives; a feature-area name keeps accumulating requirements as later phases, or future changes, touch the same area. Accept that phases sharing a capability serialize their archive; the phases that collide on files usually collide on capability too.

#Example 3: A brownfield system (adopt, intake, promote)

In the interactive guideAdopt a codebase Route every change

The project: legacy-pay, a production payments service built long before HSDD: no specs, some tests, three teams in CODEOWNERS (payments, treasury and platform). A PRD arrives: merchant payout scheduling. Instead of speccing the PRD as its own project, adopt the system once, route the PRD into the tree, and promote only the node the change lands on. Cost scales with the number of seams (routes, topics, tables, owners), never with lines of code: the skill extracts structure by script and reads nothing else.

This example adopts a whole repository. The same steps, scoped to named modules, adopt the code around an already governed tree; see the end of the example.

#Step 1: Extract the seams

prompt
You: "Adopt this codebase into HSDD."

hsdd-adopt first copies its scripts verbatim into hsdd/scripts/seams/ (the same precedent as the registry generator) and adds .hsdd-seams.json to .gitignore and commits that line, then runs the extractor:

bash
node hsdd/scripts/seams/extract-seams.mjs extract -o .hsdd-seams.json

The model records what tooling can see, stamped with the commit it looked at: manifests (package.json, go.mod), modules (src/billing, src/payouts, src/merchant, db, cmd/server), route registrations with their file:line, schemas (src/payouts/openapi.yaml, src/merchant/schema.graphql), migrations and the tables they create, topics produced and consumed, CODEOWNERS, and which directories change together in git history. Routes and topics are regex candidates; the model says where each came from. .hsdd-seams.json is scratch and is never committed.

#Step 2: Confirm the tree before any node spec or contract is written

The skill proposes a shallow tree on the seams that exist and stops:

text
legacy-pay                     (root, internal)
  legacy-pay.billing           leaf-parent, as-built   src/billing   @payments-team

#Running the project

In the interactive guideEvidence and milestones

Planning artifacts tell you what to build; the management layer tells you how it is going. Once implementation starts and more than one person is involved, add a weekly rhythm on top of the loop you already have.

#Two roles

HSDD work splits across two roles. The split is real but not clean. On a small team one person wears both hats, and the handoffs matter more than the labels:

Developer Lead / manager
Plan drafts the decomposition, contracts, and phase plans (hsdd-spec, hsdd-contract, hsdd-adr, hsdd-phase-plan), often sitting with a lead for the axis call verifies the result: is the ownership axis right, are contracts frozen where they must be, are phases sized to the window? Arbitrates hsdd-reconcile
Execute owns it: phase context switch, OpenSpec cycle, TDD, gate, verification doc reviews at the tier the phase declares; full-review phases get real attention
Manage supplies the evidence, because a phase is done only when its verification doc is merged to main owns it: hsdd-checkpoint weekly, hsdd-milestone at generation and re-baseline; carries the stakeholder conversation

The one hard rule in that table: the lead verifies the decomposition before phases open. A wrong ownership axis reworks every node beneath it, and it is cheapest to fix on the day it is drawn.

Read the two edges out of the management band as the loop that keeps the project honest. Evidence flows up: a phase is done when its verification doc is on main, and nothing else counts. Work flows back down as named steps, into execution and into the spec tree when the review found drift.

#The weekly checkpoint

Before the team sync, the lead runs:

/hsdd-checkpoint full checkpoint before Monday's sync. Repos: ~/git/acme-be, ~/git/acme-fe.

The skill makes one evidence pass over the spec repo and every implementation repo, then writes four outputs:

  • a dated progress report: what is actually done, velocity, ranked blockers, and a findings register;
  • a dated execution plan that supersedes last week's: a plan graph of the week's shape; a section for each sync the week depends on, with its entry criteria, the decisions it settles, its exit criteria and what it unblocks per lane; step tables where every step carries a detail block; external tracks; and append-only guardrails;
  • a regenerated atlas, hsdd/management/atlas.md, with the tree and its phase status, the contract graph and the ADR coverage map;
  • ticked milestone gates.

Pass the repo paths in the prompt. They differ per machine, and the skill asks if you leave them out. Every finding becomes a plan step or an explicit waiver: the review compiles into next week's work, it never just advises.

The plan is written for its readers, not its author. Agent-run steps (🤖/🤝) carry the exact prompt to paste and a Validate: line. Human-only steps (👤) carry a Why / Do / Done when briefing, the fullest write-up in the plan rather than the tersest, because an agent mid-task can be re-prompted while the human at Monday's sync has only what the plan gave them.

When new context lands mid-week (a PRD revision, a design drop, a decision):

/hsdd-checkpoint scoped. New context landed in commits abc1234 and def5678; check spec integrity against it and revise the plan.

The pass narrows to the touched artifacts plus their closure, and patches the plan the same day instead of letting drift pile up until Friday.

#Reading aids

Two optional pages, both one offline HTML file under hsdd/summary/, both derived and never edited:

  • The plan page (summary.html): the tree from the root's parts down to each phase's card, with What to check at every level, for a reviewer, a stakeholder or an implementer. Render it after a spec level or a phase plan, so the reviewer opens it in the same MR:

    /hsdd-summary render the plan page.

  • The checkpoint page (checkpoint.html): the newest progress report and execution plan laid out for the sync. The lead sees the read, the gates and their movement, the syncs, the plan graph, the blockers, and how long each finding has been carried; each executor picks a lane and works its steps in order, copying prompts from the page; stakeholders see the verdict and the milestones in plain words. Once hsdd/summary/ exists, every checkpoint renders it at step 7, before the commit lands.

/hsdd-summary check lists any page or prose that has gone stale.

#Milestones

Once every leaf-parent in the campaign's scope is phase-planned, which is the first moment total scope is computable, generate the stakeholder document:

/hsdd-milestone generate the milestone document.

Each milestone is a demo (something a stakeholder can watch work) plus a gate (yes/no checkboxes). Externally-gated phases go to the contingent tail: excluded from the launch gate, each with a pre-agreed degradation path, so an external team's silence is a plan rather than a slip. The weekly checkpoint ticks the gates. hsdd-milestone runs again only to re-baseline, on a gate red two checkpoints running or a scope change the dates cannot absorb, and a re-baseline states the old window and the new one together, so slips stay visible.

#Open questions

Open questions get the same discipline as contracts: minted once in the owning spec (OQ{n} at the root, OQ-B3-style in nodes, prefixes declared in conventions.md) with a status table (OPEN / PARTIAL / RESOLVED (date)); every other artifact cites the ID. Phase plans mark contingent phases contingent (OQ-…), and both the milestone tail and the checkpoint's health pass are built from those markers. An ID that is cited but never defined, the classic OQ-B3 phantom, is a finding, not a typo.

#Multi-repo projects

When backend and frontend live in separate repos, keep the HSDD tree in its own spec repo and mount it as a git submodule at hsdd/ in each implementation repo (Profile: standalone-spec-repo in conventions.md). Because the mount point is hsdd/, every path you already know, such as hsdd/spec/…, hsdd/contract/… or hsdd/management/…, stays literally correct, and no skill needs a profile-specific path.

What the profile does change is where you run: every /hsdd-* skill runs from an implementation repo, never from a standalone clone of the spec repo. A standalone clone is a third working copy whose edits leave every submodule pointer behind, and a session without the code cannot verify what it asserts. Governance edits are committed and pushed inside the submodule, then each implementation repo's pointer is bumped.

Four rules keep the truth unforked, each one written after an incident:

  1. Submodule pointers only ever reference spec-repo main commits.
  2. A phase is done when its verification doc is on spec-repo main, the same day as sign-off, not parked on a branch.
  3. Branch pairs spanning an implementation repo and the spec repo land together or are discarded together, never one side alone.
  4. Never squash-merge a multi-phase epic: per-phase history is your velocity data and your audit trail.

#Adopting on a project already underway

The first /hsdd-checkpoint is an adoption run. Existing management documents become the head of the supersedes chain, existing numbered guardrails keep their numbers, nonconformances become findings with migration steps rather than errors, and the first atlas is generated however messy the tree is. Historical documents are never rewritten; conformance starts from the next document forward. To move the project itself to a newer release, see Upgrading.

#Unattended runs

In the interactive guideRun unattended

/hsdd-auto plans the tree, or routes one change request into it, without you at each ask point. It dispatches one fresh subagent per skill invocation, gates and commits every step, and records every decision. It never implements a phase, never runs hsdd-config and never passes a review gate. Your review moves from each ask point to one sitting over the decisions afterwards. The meeting-rooms tutorial is a recorded intake run: 31 steps, 231 decisions, no stop, and the owner's review in one sitting.

Start it from a clean working tree in the repository that holds hsdd/, with Node.js 20 or later and the six planning skills installed.

#First run

With no hsdd/auto/run.yaml on any local branch, /hsdd-auto asks ten questions in one batch, each with a proposed default: the run's name, root, branch, base and skills directory; who builds what; the sources; read-only and out-of-bounds paths; owner facts; toolchain prefixes; stop policy and stop set; owner files; prose rules; commit trailers. The proposals come from node hsdd/scripts/auto/state.mjs defaults plus the root spec's ## Sources, hsdd/conventions.md and your agent instruction files. It writes the answers to hsdd/auto/run.yaml and never asks again. Answer "decide" to who builds what and the root step decides the axis itself and records it with would_have_asked: true. Later configuration changes are setup decisions of a new segment. run.yaml lives on the run branch: run /hsdd-auto from another branch and it names the branch that holds the file and asks you to check it out, instead of asking the questions again.

#Plan and intake segments

A run is made of segments. Each one is opened by one instruction from you, runs in one mode under one stop policy, and ends with one report.

A plan segment, /hsdd-auto, plans an empty tree through reconcile: the root decomposition, the ADRs and contracts it names, each mid-level node, each leaf-parent's phase plan, the consistency items, an align, and the report.

An intake segment, /hsdd-auto intake {request path}, routes one change request: hsdd-intake writes the record, then one step per handoff the record names, then the consistency items, an align and the report. --authority accepted-rfc|approved-prd|draft|ticket|incident|braindump states how much the request binds (default draft). It never closes the intake record; the checkpoint does, as for any intake.

/hsdd-auto status shows where the run is and changes nothing.

#The stop policy

You choose it per segment with --stop-policy stop|decide-and-record. Under stop, a stop-set condition (axis, shape, promotion, breaking-amend, collision, external, gate-twice) ends the run with hsdd/judgement/STOP.md. Under decide-and-record the run decides it and records the decision with would_have_asked: true and the class. Either way, external with no in-repository alternative, a second gate-twice and three other hard stops end the run with STOP.md. When a segment will meet one class many times (an intake that breaks several stable contracts), decide it once, under decide-and-record only: the decision goes into predecided in run.yaml and every later prompt carries it. A predecided answer never covers a breaking change to a frozen or v0 contract. A breaking-amend answer, predecided or given to STOP.md, names the migration mode, coexisting or lockstep; when it names none, the step decides the mode and records the decision for your review.

#Answering STOP.md

hsdd/judgement/STOP.md holds the stopped step, the stop class, the question verbatim, the options with a recommendation, what the stop blocks, and how to resume. A bare /hsdd-auto is refused while it exists. Answer in one message and run /hsdd-auto with it: the answer opens a new segment, is recorded as an owner decision, and the stopped step continues with it.

#Reviewing a segment

The review is one sitting over the segment's records:

  1. Read hsdd/auto/report/{segment id}.md. The report's "Decisions to look at first" section lists every answer the run gave on your behalf (the would_have_asked decisions); the other sections cover the steps, the assumptions about your intent and what the generated record leaves out.
  2. For each decision you disagree with, or that the run should have asked you, append a line to hsdd/judgement/decision-reviews.jsonl: decision, at, review (agree, disagree or should-have-asked) and a reason for the last two. The run never writes this file.
  3. Guidance: to reverse a decision, write the reversal as a short request document and route it with /hsdd-auto intake {path}, or run the owning skill yourself.
  4. /hsdd-summary re-renders the reading aids afterwards; the run does not drive it.

#Outside the loop

Four situations recur on real projects, and the loop above does not name them: a stakeholder wants a size before any spec exists; the team keeps a knowledge base the spec should draw on; a launched system takes small fixes faster than phases can be planned; and a released tree has gone stale and nobody will verify it phase by phase. Two of them run on the skills as they are: what changes is the prompt, and in one case a section you add to hsdd/conventions.md, the file every skill reads first. The third is hsdd-intake's manual class and sweep mode. The fourth has a skill of its own, hsdd-seal, because it is clerical work a script does better than a model.

#A knowledge base beside the tree

Karpathy's LLM Wiki is a local git repository with immutable source documents under raw/, pages an agent writes and maintains under wiki/ with an index.md and a log.md, and a CLAUDE.md that is the wiki's schema: how pages are organized and how the three operations run, ingest, query and lint. The skills do the rest under the trickle-down rule: the sources a node needs land in its Sources, and the phase context later carries the sections the phase cites. Nothing reaches a coding session by any other path.

Ingest back. After hsdd-reconcile or a checkpoint, run inside the clone:

text
You are working inside the LLM Wiki at this directory; follow its CLAUDE.md.
Ingest the HSDD governance that changed in ~/git/acme since 2026-10-26:
hsdd/adr/, hsdd/contract/ (contract files only, not fixtures) and the
intake records under hsdd/management/. Treat them as sources that live
outside this wiki: create or update entity pages for the system, its nodes
and its contracts as pointer pages, each saying what the artifact is and
linking its path, never restating a decision, an interface or a phase. If
the wiki's conventions require a copy under raw/, copy with the repo commit
sha in the filename and keep the pointer rule for the page. Update index.md
and log.md. Reply with the pages touched.

Three failure modes to watch. A wiki page can lag the raw document under it; that is why the raw document sits in Sources too, where a version move is a citation touch. A session that reads the wiki at large instead of a filed answer pulls an unbounded amount of text into its context; the filed-answer rule exists for that. And a public tree over a private wiki leaks nothing as long as Sources lines stay one line and a pointer, which is what the rule already says.

#Small fixes and small requests on a launched system

After launch, most changes are small: a font size, a line of copy, a log line, a null check. A full phase costs the same for a twenty-line fix as for a feature, so HSDD gives these changes a cheaper path. Come back to this section whenever you have a change and are not sure what to do with it.

Everything here applies only after launch. Before launch, a fix belongs to the phase it fixes, on that phase's branch.

#How hsdd-intake handles a change

hsdd-intake is the one skill you need for any change after launch. You do not decide how big the change is: the skill does that for you. It has two modes, and the mode depends on whether the code exists yet.

Mode Use it when Command Result
Request mode the code does not exist yet /hsdd-intake route ... a class that says what the change needs
Sweep mode the commits are already on the main branch /hsdd-intake sweep a sweep record with one row per commit

Both modes ask the same two questions about a change:

  1. Does the change move the contract surface? The surface is what other nodes can see: routes, schemas, topics and tables. A change that moves the surface is not small, however few lines it has. It needs an intake and a contract bump.
  2. Does the change make a claim in the tree false? A claim is a sentence in the tree that the code can make false without moving the surface: a phase's Scope or Verification line, a Guarantee of a contract the node produces, or the Decision of an ADR that governs the node. Suppose a Verification line says "the preview shows the fee line", and you rename that line to "charge". The sentence is now false, so the change needs a phase, because the tree must not say something the code no longer does.

When both answers are no, no other node can see the change, and the tree needs only one fact from it: which node it happened in. Before the code, intake writes nothing. After the code, the sweep writes one table row. On an as-built node the second question is not asked: only the surface decides, and promotion waits for the first change that needs a phase.

Sweep mode asks one more question before these two, because it looks at commits that already exist: is this commit the work of a phase? Many commits on the main branch are. When several developers commit at the same time explains how it decides.

The answers give the change a class.

Classes in request mode:

Class Means What happens next
manual no surface moved, no claim made false, inside one node Nothing is written. You get a node and a commit trailer, and you make the change.
local fits inside one leaf-parent and needs a phase A record, then a phase on that node.
cross-node touches the surfaces of several nodes A record, a contract bump or an ADR, then a phase on each node.
new-capability needs a node that does not exist A record, a new node under the existing parent, then its phases.
structural the shape of the tree is wrong for this change A record with the options written down, and a person decides.

Classes in sweep mode, one per commit:

Class Means What it costs
log no surface moved, no claim made false One row, which is the whole record of the commit.
phase the commit is the work of a phase One row that names the phase. The phase's own gate and verification doc cover the commit.
retro no surface moved, and the diff makes the claim in the row false One phase per node per record, however many commits it lists, with its reconcile and a retroactive verification doc signed by delegation.
intake a surface moved, or the paths span two nodes One run of request mode per row, with authority commit. The phases it produces are retro phases, and the contract bump it orders is the one the code already made.
unplaced no node owns the paths and nobody placed the commit No handoff. The report names the row, the next checkpoint files it as a finding whose step is hsdd-adopt on the paths, and the record stays open until a person places the row, which hsdd-adopt alone does not do.

Which node? Both modes need to know which node owns the code. When you do not know, ask:

text
Read hsdd/management/atlas.md (hsdd/spec/ if there is no atlas). Which node
owns these paths: src/payouts/schedule.ts,
src/payouts/__tests__/schedule.test.ts? Use each node's Isolation strategy,
its phases' Scope lines, and any `modules:` line under an Observed surface.
Answer with one node id and the phases whose Scope names these files, or
say the paths span two nodes and name both. Write nothing.

Two nodes is the first sign the change is not small.

#Before the code exists: ask hsdd-intake first

Route the request, however small it looks:

text
/hsdd-intake route docs/tickets/PAY-431.md (ticket): add the merchant id to
the log line when a payout preview fails. Small, inside payouts.

If the answer is manual. Intake asks both questions about the request as you described it. This request moves no surface and makes no claim false, so it is class manual, and the skill writes nothing under hsdd/. Its report:

text
Class manual, no record.
Node: acme.backend.payouts
Trailer: HSDD-Node: acme.backend.payouts
Ship it on the main line. It is attributed by /hsdd-intake sweep after it
merges, by you or by a lead before the next checkpoint. If you find the
change moves a route, schema, topic or table, bring the request back through
request mode before it merges.

Put the trailer on the commit:

text
payouts: merchant id in the preview failure log

HSDD-Node: acme.backend.payouts

There is no record, because the row the commit gets in the next sweep is the audit trail. The trailer only tells the sweep which node the commit belongs to. It does not attribute the commit on its own.

You get manual only when you run the skill yourself. An unattended run (/hsdd-auto intake) never answers manual: it routes the same request as local and records that decision, and the segment review then shows a phase you did not need.

If intake cannot tell. When your description does not settle the two questions, the class is not manual. A phase is the safe answer, and a sweep can still find later that the diff was small.

If the change needs a phase. A product request is a different case. PAY-412, "show the fee line in the payout preview", adds behavior the tree must describe, so its class is local: a phase. It goes through intake as usual. The saving is in asking the next skills for the smallest phase. Route it:

/hsdd-intake route docs/tickets/PAY-412.md (ticket): merchants want the payout preview to show the fee line. Small, inside payouts.

The record lands as class local with the handoff prompt written in it. Run it, and ask for the smallest phase the rules allow:

text
/hsdd-phase-plan acme.backend.payouts per
hsdd/management/2026-11-02-intake-pay-412.md: append the phases this ticket
needs. I expect one, review tier spot-check, gate "npm test -- payouts",
Verification: the preview shows the fee line for a scheduled payout. If you
need more than one phase or a contract change, say why before writing.

Then /hsdd-reconcile acme.backend.payouts drains the pending section. A lone appended phase with no governance updates takes a few seconds. /hsdd-phase acme.backend.payouts.9 writes the context, and the fix runs as a cycle or by hand. Either way, the phase is done when its verification doc is on main:

text
Write hsdd/verify/acme.backend.payouts.9.verification.md from
hsdd/templates/verification.md for the fix in commit 8c1e4f2: the commands
that prove it, what you observe when you run them now (dated), Outstanding
for anything you could not run here, Learnings or "- none". Sign-off:
Claude for {owner} (delegated), tier spot-check. Run the commands; do not
invent an observation.

The next checkpoint appends the phase to the record's ## Produced, ticks the record closed, and lists the delegated sign-off for the owner to ratify. If you do not want to run these steps one by one, run the chain unattended and read its decisions afterwards in one sitting:

/hsdd-auto intake docs/tickets/PAY-412.md --authority ticket --stop-policy decide-and-record

#After the code is on the main branch: run a sweep

Run a sweep for a hotfix, for a QA finding you fixed on the spot, and for a change that got a manual answer. The spec calls the first two the legal bypass: ship the fix, then sweep it. From the implementation repository's root, the directory that holds hsdd/:

text
/hsdd-intake sweep --run-by "Dewi Lestari"

Your first sweep also needs a starting point: see The first sweep. The first sweep also copies the script into hsdd/scripts/sweep/. The script needs Node 20 or later.

What a sweep does:

  1. The script reads every commit from the end of the previous sweep to the head of the main branch.
  2. It sets aside the commits that need no row: merges, governance-only commits, commits whose message names a phase id, commits a phase's Scope cites, and commits an earlier record classified.
  3. Every other commit gets a row. The script checks each one for a surface move and proposes a node, from the HSDD-Node: trailer or from the one modules: line that covers every path.
  4. The agent asks whether the commit is the work of a phase, then whether it makes a claim false, and fills in the rest of the row. It asks you once about anything the tree cannot answer.

The result is a record such as hsdd/management/2026-11-12-sweep-acme-be-e91b2d4.md:

Commit Node Class Reason Subject
a4e19c7 acme.backend.payouts log none payouts: merchant id in the preview failure log
b81f3c2 acme.backend.payouts phase acme.backend.payouts.10 payouts: schedule preview shell
5d2b9a0 acme.backend.payouts retro acme.backend.payouts.9 Verification: "the preview shows the fee line" payouts: the preview's fee line reads charge
c7d03be acme.backend.payouts intake route added GET /payouts/fees payouts: fee lookup endpoint
e91b2d4 none unplaced src/legacy/report.ts report: null check

What happens next. The record's ## Routing section holds the filled prompts for the retro and intake rows. The agent runs them in order, or hands them to whoever will. log and phase rows need nothing more, and a record of only those rows is written closed by the sweep itself. The next checkpoint closes any other record once every retro and intake row has its product in ## Produced and no unplaced row remains.

Changing a class. Raising a class means moving it toward more work, such as from log to retro. The agent may raise a class but never lowers one. You may lower any class before the record is committed, with a change-log line that names you. After the record is published, nobody lowers a class.

Committing the record. check and commit guard the first commit of the record. check reads the record back against a fresh draft of its range and refuses with the row named. commit commits the record alone and never pushes. Under the standalone-spec-repo profile, push inside hsdd/ first and the implementation repository second, as with every governance edit. Otherwise the submodule pointer names a commit that no other clone has. A later edit, such as placing an unplaced row, is committed with git directly.

#The first sweep

On the first sweep, name the start with --from. The commit you name is not swept itself, so give the last commit of the launch:

text
/hsdd-intake sweep --from 3fa81c0 --run-by "Dewi Lestari"

Later sweeps start where the previous record ended. A --from later than the previous record's end is refused, because it would leave commits no sweep reads. An earlier one is accepted, and the overlap is set aside as classified. A range with no candidates writes no record.

#Who runs it, and how often

Anyone can run a sweep: a developer after merging, or a lead before a checkpoint, with the same command and the same steps. The record's Run by line names a person, who answers for the classification. A lead who sweeps the week's commits does not answer for the code. When an agent runs the sweep and no person reads the record before it is committed, name the delegation:

text
/hsdd-intake sweep --run-by "Claude for {person} (delegated)"

The next checkpoint lists a delegated sweep with the delegated sign-offs, for that person to ratify.

You may wait for the checkpoint. Commits nobody swept become one backfill finding per repository, whose plan step is /hsdd-intake sweep --from {sha}, never a retro phase per commit. With sweeps in place, run /hsdd-checkpoint scoped after a batch of fixes, naming the commits, and full only before a release. Weekly is a convention, not a mechanism.

#When several developers commit at the same time

On a team the main branch is a mix. Ana delivers a phase for one intake, Budi delivers a phase for another, and Citra merges a small fix between their commits. A sweep handles this, and nobody has to coordinate anything first.

One range for everyone. A sweep reads one continuous range, from the end of the previous sweep to the head, not one range per developer or per problem. The author of a commit plays no part: each row lands on a node by the paths it touched. If a colleague merged three commits after your hotfix, the sweep classifies all four. One person can sweep everyone's commits.

Put the phase id in every commit of a phase. This is the one habit that matters:

text
acme.backend.payouts.10: schedule preview totals

A commit that names its phase needs no row, no question and no judgment. hsdd-config writes this rule into every phase context, so an agent running a phase follows it. Hand-written commits are the ones that forget.

When a phase commit does not name its phase. The agent reads the phases of the owning node. The commit is the work of a phase when the diff lies within what the phase's Scope says, and the commit is no later than the phase's sign-off. The row then gets class phase, with the phase id as its reason. Three rules keep this honest:

  • Sharing a node is not enough. A small fix on a node with an open phase is not that phase's work.
  • A phase whose verification doc is signed does not take later commits. A fix after the sign-off is an ordinary row.
  • A commit that touches two nodes stays intake, because a phase belongs to one node.

A phase often moves the surface on purpose, for example by adding a route it planned. The script still marks that commit intake, and the agent changes it to phase when the phase's Scope or Produces accounts for the move. When the agent cannot tell, it asks you once. A commit nobody claims for a phase goes on to the second question.

One week on acme.backend.payouts:

Commit subject Author What the sweep does
acme.backend.payouts.10: schedule preview totals Ana sets it aside: the message names the phase
payouts: schedule preview shell Ana a phase row: the Scope of acme.backend.payouts.10 describes it
payouts: larger font on the total Citra a log row: no phase describes it, and no claim is false
acme.backend.ledger.7: release a hold Budi sets it aside: the message names the phase

Two people sweeping. A sweep starts where the newest record ends, so pull before you sweep, and under the profile update hsdd/ as well. When two people sweep the same commits, both records list them, and the next checkpoint files that as a finding. Nothing blocks it, so agree who sweeps. The simplest answer is one person, such as a lead before a checkpoint.

Work still on a branch. A sweep reads only the main branch, so commits on an unmerged branch wait. When the branch merges, the merge is set aside, and the commits it brought in enter the next sweep's range like any others.

#Sealing a released tree

This is for a system that shipped, that QA verified, and whose tree then went stale: verification docs unsigned, phases planned and never built, intake records open, an execution plan full of syncs nobody will hold. Rebuilding the history is the expensive path, one retro phase per manual change, and reviewing what it generates is harder than the work it records. Sealing costs one script run and spends your attention only where the next change will look: which phases shipped, and the contracts and ADRs.

Everything the seal needs is already admissible. A sign-off an agent takes for a named person counts as done, and the next checkpoint lists those sign-offs in one finding for that person to ratify. An Outstanding item may be waived with a reason. A verification doc written after the fact is the retroactive doc the spec's bypass rule names. An intake record closes when its produced phases are done. A campaign whose gates are all green is sealed and archived. And a protocol stated in conventions.md reaches every skill. Before v0.12 the method had no status for a phase that was planned and never built; v0.12 §3 names one, - **Status:** dropped (date, reason) on the phase record, mirroring node retirement. The seal writes it, and a project on older skills restates in every checkpoint prompt that dropped phases are out of scope.

Nothing in a seal needs judgment except which phases shipped, and that is your knowledge, not a model's. So the seal is the hsdd-seal skill's script: it computes a plan from the tree, you edit one field, it applies the plan, and no model reads a file. On a project billed per token that is the difference between a seal and a week of review. Copy the skill's scripts/ directory verbatim to hsdd/scripts/seal/ (Node 20), then plan:

bash
node hsdd/scripts/seal/seal.mjs plan --release 2.4.0 --date 2026-09-15 \
  --owner "Dewi Lestari" --evidence "QA regression 2.4.0, Jira PAY fix version 2.4.0" \
  --catchup a1b2c3d..f4e5d6c

--catchup names the commits an earlier catch-up attempt made (a revspec, since:YYYY-MM-DD, or comma-separated shas), so the plan can tell which verification docs and OpenSpec change directories were invented after the fact. The value is checked before anything is read, and under the standalone-spec-repo profile only since: reaches both the implementation repo and the submodule. The command writes hsdd/management/{today}-seal-plan.json and a markdown rendering, with a default class per phase: done (a signed doc), sign (the newest progress report counts it done, its phase context exists, an OpenSpec change names it, or a doc existed before the catch-up), drop (nothing else), skip (already dropped, or a retired node). When in doubt the default is drop: a built phase wrongly dropped is re-planned by a later intake; an unbuilt phase wrongly signed makes the contracts claim behavior the code lacks. Read the markdown once, edit the class field in the JSON where the default is wrong, and leave everything else: the script re-derives every path at apply time and refuses one that leaves the project root. Then:

bash
P=hsdd/management/2026-11-03-seal-plan.json
for step in sign drop prune close; do
  node hsdd/scripts/seal/seal.mjs apply $step --plan $P                   # dry run, read it
  node hsdd/scripts/seal/seal.mjs apply $step --plan $P --write --commit  # apply, commit "seal: $step"
done
node hsdd/scripts/seal/seal.mjs report --plan $P --write --commit
  • sign writes a retroactive doc for every sign phase whose doc is missing or was added by the catch-up: Observed reads "Not observed by this run. Released in 2.4.0 on 2026-09-15. QA evidence: ... Retroactive (spec §11.8)", Sign-off reads Claude for Dewi Lestari (delegated), {today}, Outstanding is waived. A doc with a real run keeps its body and gets only its Sign-off rewritten; Learnings it already carries are sealed as dropped (sealed at release 2.4.0; not actioned) and the report lists the phase, because the seal never claims a disposition nobody made.
  • drop adds the Status line after each dropped phase's Review tier and the convention paragraph under ## Phase design in hsdd/conventions.md.
  • prune deletes each openspec/changes/ directory whose every file the catch-up added; they record cycles that never ran, and the retroactive docs carry the honest record. openspec/specs/ is never touched.
  • close re-scans, closes intake records whose produced phases are all done, closes one whose produced phases were all dropped as closed (date, dropped), ticks every gate whose phases are done or dropped, records the dropped ones in the milestone's change log as an absorb, and when every gate is ticked adds - **Sealed:** {today} and moves the document to hsdd/management/archive/.
  • report appends a ## Result to the plan markdown with the counts and a Needs the owner list: request entries for hsdd-reconcile, gates still open, records still open, Learnings to read, catch-up docs left on dropped phases, unparsed items. That list is the whole of what you act on afterwards.

Every step is a dry run until --write, is idempotent, and with --commit commits only the paths it touched (under the profile: inside the submodule, then the pointer bump; it refuses to write while hsdd/ has a detached HEAD). One decision before you run it: everything in the campaign must end up done or dropped, because hsdd-milestone keeps one unsealed document at a time. Work you want to keep for later (--keep) holds its gate red and belongs in a new campaign generated after the seal; the simpler path is to drop it and let it re-enter through hsdd-intake.

What you have afterwards is a tree whose ledger is complete and honest: every shipped phase has a doc that says it was not individually observed and why that was accepted, every unbuilt phase says it was dropped, the campaign is in the archive, and your remaining work is the Needs the owner list. No checkpoint ran: the expensive evidence pass was paid for before the seal and nothing in the code changed. The first checkpoint after it, scoped to the seal commits, supersedes the pre-seal execution plan, lists the seal's delegated sign-offs in one finding for you to ratify, and carries the standing decision that every finding except a contract or ADR item is waived "sealed at release 2.4.0". A reconcile runs when the first intake needs one. New work enters through the lanes of the previous section; a feature large enough for several phases enters through hsdd-intake and opens a new campaign.

#Tips

  • Size to the window. If a phase will not fit one ~5h review window (AI run plus your review and verification), it is too big. Ask hsdd-phase-plan to split it. Too small is also a smell: merge adjacent phases under the sizing floor's conditions (same tier, same consumed contracts, no third phase depends on one without the other, still fits the window) rather than paying a full cycle for a phase that will not earn it.
  • Switch context before opsx:new, every time. This is the one easy-to-forget step. /hsdd-phase {phase-id} exists for exactly this.
  • Config conflicts are noise. A merge conflict on openspec/config.yaml's Current Phase block carries no information, because the block is ephemeral per-session working state. Take either side and re-run /hsdd-phase {next-phase} before the next cycle.
  • Add a level, do not widen. When a leaf-parent grows past a handful of phases, insert an internal node ("feature") instead of piling on phases.
  • Split where ownership splits. Decompose along team, owner, or deploy-target boundaries first (backend vs. mobile vs. web); capability slicing over technology buckets applies only within one owner's territory.
  • Point at the doc, don't paste it. When the spec is generated from PRDs or RFCs, the root's ## Sources section and each node's Sources field keep them reachable. A summary thins at every level; the pointer does not. Phase planning reads the node's sources, not just the node spec.
  • Keep hard edges rare. They are the critical path. Prefer contract, event, and shared-model edges so teams parallelize.
  • Plan against frozen governance. hsdd/contract/, hsdd/adr/, and hsdd/conventions.md are read-only during phase planning, even at the root. Changes ride the plan's pending-governance section until hsdd-reconcile applies them; never resolve a contract gap by editing the contract mid-plan.
  • Regenerate the registry after any contract or ADR change: node hsdd/scripts/gen-registry.mjs. Never hand-edit INDEX.md.
  • Materialize ADRs as files, not prose. A cross-cutting decision belongs in hsdd/adr/{nnn}-{title}.md with frontmatter (via hsdd-adr), so the registry and the phase context can find it. A decision internal to one node stays a D{n} in that node's spec.
  • Match review depth to risk. Reserve full-review for orchestration, business logic, integrations, and security. Let scaffolding be gate-only.

#Upgrading

Upgrades are additive: reinstall the skills, and nothing already written is rewritten. Each release's entry in the changelog has the full list of changes. The notes below say what changes for a project in flight, newest release first.

#From 0.13.0 to 0.13.1

Reinstall the thirteen skills. Nothing is rewritten. A sweep now tells the work of a phase from a small fix: such a commit gets a phase row, even when it names no phase id. Records already written stand. A first change-log line with no phase count reads as zero. The checkpoint attributes phase work again, so a backfill finding that named only phase work closes without a sweep. That is all a project that never sweeps sees of this release. Every commit of a phase should now name its phase id. Phases switched after the upgrade get that line in their Discipline. A phase context already written is a record and is not rewritten.

#From 0.12.0 to 0.13.0

Reinstall the thirteen skills. Nothing is rewritten. The manual class applies from the next request forward and writes no record. Sweep mode is opt-in: a project that never sweeps is unaffected, its post-launch commits with no phase are backfill findings as before, and the finding's step now names a sweep. The sweep record is a new management document outside the chain rules, and the reading aids ignore it by its slug. The commit authority is a new value of an existing field, so existing records are unchanged. A retro phase over several commits is forward-only: retro phases already planned stand. A commit whose retro phase cites it by sha is attributed. A retro phase that cites only a finding id attributes nothing, so start the first sweep after such commits. The amended scripts rule changes nothing on a project: request mode runs no script.

A project that adopted the manual lane from the 0.12 guide is conformant: its trailers are read as hints, its same-day retro phases stand, and its first sweep names its own --from. Remove the ## Manual lane paragraph from hsdd/conventions.md if you added it. It conflicts with the checkpoint's attribution rule, and the first checkpoint after the upgrade files it as a finding whose step removes it.

#From 0.11.0 to 0.12.0

Reinstall the thirteen skills. Nothing is rewritten. The dropped phase status (- **Status:** dropped (date, reason) on a phase record) is recognized from the next checkpoint: out of every scope and done count, its row kept. An intake record whose produced phases were all dropped closes as closed (date, dropped). A project that never seals is otherwise unaffected; one that already carries the convention paragraph under ## Phase design keeps it as informative text.

#From 0.10.2 to 0.11.0

Reinstall the twelve skills. Nothing else changes unless /hsdd-auto runs: the skills' new ## Unattended runs sections are inert unless a skill is invoked with --unattended. A hsdd/judgement/decisions.jsonl written by a hand-built unattended run continues under hsdd-auto; its lines read as legacy lines, with one warning.

#From 0.10.1 to 0.10.2

Nothing is rewritten: reinstall the skills. The change flow gains the rules the second tutorial found missing:

  • A later contract version is its own file, {slug}.v{n}.md, beside the first.
  • A breaking change's migration note names its mode, and a lockstep bump (one endpoint, one shape) deprecates the old version at once.
  • The checkpoint finds consumers that migrated and reconcile moves them to former_consumers, so consumers means live.
  • Reconcile, not append mode, writes a new version into the node headers and the root spec.
  • A phase line carries the detail it relies on, not a pointer to a source, and the phase context now carries the node decisions (D1) a phase cites.
  • A sign-off an agent takes for you names you, counts as done, and comes back to you at the next checkpoint to ratify.
  • The superpowers derivative names the skills it relies on: test-driven-development on every task, verification-before-completion, systematic-debugging, and the execution skill by review tier.

Absent fields keep the 0.10.1 behavior; the spec's §15.1 has the table.

#From 0.10.0 to 0.10.1

No artifact changes: reinstall the skills, and the next phase switch adds each contract's Validation section and any referenced contract to the phase context. A superpowers phase already in progress keeps the context it started with.

#From 0.6.1 or later to 0.10.0

The upgrade is additive and nothing is rewritten. The first checkpoint after upgrading runs the upgrade behaviors, although the project already has a checkpoint chain; you can tell it is the first because its newest progress report has no grandfathered-contracts row. Each new rule states its effect in the spec's upgrading chapter: absent fields default to the old behavior, and Learnings/Metrics apply to future verification docs only.

  • Ordering policy. A conventions file that still carries 0.7.1's FP ordering: bullet keeps fp-progression; add **Ordering policy:** fp-progression to say so, or remove the bullet to take interfaces-first.
  • Executable validation, grandfathered and discharged on touch. The one rule with teeth is that stable contracts need executable validation. The upgrade checkpoint lists every existing fixtureless stable contract and emits one plan step; hsdd-reconcile marks each validation: grandfathered; the set is closed. A phase that next touches such a contract cannot pass its gate until its schema or fixtures exist, written at the root through hsdd-contract; the next checkpoint then files a discharge finding and reconcile removes the mark.
  • Counting down. Every progress report shows the remaining count next to the previous one and cites the upgrade step that names the set. A contract carrying the mark that the step does not name is a High finding. A checkpoint that runs before anyone has executed the marking step carries the step forward unchanged.
