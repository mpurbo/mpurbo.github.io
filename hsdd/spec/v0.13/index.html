HSDD: Hierarchical Spec-Driven Development (v0.13 delta: the sweep, a mode of intake)

  • Version 0.13.1
  • For review
  • 2026-11-05

Source: spec/hsdd-spec-v0_13.md on GitHub

Delta specification. It gives hsdd-intake a second mode, the sweep, and a fifth class, manual, so that one skill is the door for every change after launch whatever its size and whether or not the code exists yet. A request too small for a phase is answered with a node and a commit trailer, no record; after it ships, the sweep reads a range of commits, sets aside what is already attributed, classifies the rest by bounded tests, writes one record, and hands off only what earned a phase or an intake. Read it against v0.10.2, v0.11.0 and v0.12.0; only the changes are stated here. Everything in those documents not touched below still stands.

#1. What 0.13 Changes and Why

#1.1 The problem

After launch most changes are small: a font size, a line of copy, a log line, a null check. The method's unit of record is the phase, and a phase costs the same for a twenty-line fix as for a feature: an intake or a backfill finding, a phase-plan append, a reconcile, a verification doc, a sign-off. FT-4 showed what happens when that cost exceeds a team's tolerance: the fixes ship, the tree stops describing the code, and the repair that rebuilds history one retro phase per change (v0.10.0 §11.8) costs more review than the work it records. v0.12.0 answered the recovery with the seal. It did not answer the steady state that made the seal necessary, and the user's guide's manual lane, written as a project convention, still costs one retro phase and one retroactive verification doc per fix.

The method needs a lane whose cost per change is one table row, with a test that says when a change has earned more. The guide already names the first test: the contract surface, not the diff size. This document adds the second, a change that makes a claim in the tree false, and gives both a home.

The home matters. A developer with a change should have one question to answer, "where does this go?", and one skill that answers it, in both cases: before the code exists, and after it shipped. If the answer before the code is "a phase" and the answer after it is "a row", developers learn to skip the question. So the lane is intake's, in both cases: a class for the request that is below the line, and a mode for the commits that already landed.

#1.2 What this release adds

  • The manual class (chapter 3): hsdd-intake's answer to a request that, as described, moves no contract surface and stales no claim, inside one node, after launch. The answer is a node and a commit trailer, no record; the change ships on the implementation repository's main line and the sweep attributes it.
  • The sweep (chapter 4), hsdd-intake's second mode: an operation over a range of commits on an implementation repository's main line. A script sets aside the commits that are already attributed, detects moves of the contract surface, and proposes a node for each remaining commit; the agent applies two bounded tests, whether the commit is the work of a phase and whether the diff makes a claim in the owning node's closure stale; the result is one class per commit: log, phase, retro or intake.
  • The sweep record (chapter 5): a dated management document, one per repository per run, that cites every commit in the range with its node and class. A log row is the whole record of that commit. The record closes when its handoffs have landed.
  • Handoffs (chapter 6): one retro phase per node per record for the retro rows, with its reconcile and its retroactive verification doc signed by delegation; one run of intake's request mode per intake row under the new authority commit; and a listing for the owner of commits no node owns.
  • The mode's packaging (chapter 7): a script bundled with hsdd-intake for the first time, under an amended scripts rule; the sweep's procedure in a file beside SKILL.md, read only in sweep mode.
  • Edits to three skills' text and one template (chapter 8): the checkpoint reads and closes sweep records and routes an unswept range to a sweep instead of a retro phase per commit; phase planning's append mode writes a retro phase over several commits; the conventions template names the new paths; the user's guide's small-fixes section is rewritten.

#1.3 What it does not change

  • The skill count. Thirteen skills. hsdd-intake gains a mode and a class the way hsdd-spec has graft and promotion modes and hsdd-phase-plan has append mode.
  • Intake's request mode for anything above the line. A request that moves a surface, needs a node, or reshapes the tree is routed as v0.10.0 chapter 11 says, record first; the manual class is the one class that writes no record, and chapter 3 says why.
  • The core invariant (v0.10.0 §1.3) and the definition of done. A log row claims nothing about verification; it says only which node a commit happened in. Nothing a sweep writes counts as done.
  • The dividing line. A change that moves a route, schema, topic or table is not small whatever its line count; it goes through request mode and a contract bump as before. The sweep detects the move and hands off; it never classifies such a commit log. The one exception is a move a phase planned: that commit is phase, and the phase answers for it (§4.3).
  • Human review. A sweep names the person it answers to, and the classification is theirs. A retro phase still gets its verification doc and its sign-off; the checkpoint still lists delegated ones to ratify.
  • Artifact formats (v0.10.0 §15.3). The sweep record is a new management document; the intake record gains nothing. commit and manual are new values of existing fields.
  • The intent of the scripts boundary (v0.10.0 §16.3, §18.1). The rule read "bundled with a new skill only; no script changes an existing skill's behavior". It now reads "bundled with a new skill or a new mode of an existing skill, and never changing an existing mode's behavior". Request mode runs no script; sweep mode runs one; the classifiers it reuses are copies kept identical by a test.
  • Before launch, nothing. A fix made before launch belongs to the phase it fixes, on that phase's branch (v0.10.0 §11.8). manual and the sweep apply after launch, like backfill.

#2. Vocabulary

  • Launched. As v0.10.0 §11.8: the system runs in production; an adopted tree from adoption, a greenfield tree from the sealing of the campaign whose gate includes launch.
  • Request mode. hsdd-intake as v0.10.0 chapter 11 defines it: one change request, routed before the code exists, record first. Its classes are local, cross-node, new-capability, structural and, from this release, manual (chapter 3).
  • Sweep mode. hsdd-intake over a range of commits that already shipped (chapter 4).
  • Main line of an implementation repository. The branch its merged work lands on, main unless the invocation names another. It is distinct from the spec repo's main line (v0.10.0 §14.2), where verification docs and records land.
  • Range. The commits on an implementation repository's main line between the end of the previous sweep of that repository and a named head, {from}..{to} in git's sense (§4.2).
  • Candidate commit. A commit in the range that the sweep must classify: not a merge, not governance-only, not attributed (§4.2).
  • Governance-only commit. A commit whose every changed path lies under the governance paths: hsdd/ (the submodule pointer included, under the profile), hsdd-context/ and openspec/.
  • Attributed commit. A commit that is governance-only, a merge, one whose message names a phase id of the tree, one whose sha a phase's Scope cites, or one that a sweep record has classified. At the checkpoint, phase work by the test of §4.3 counts as well (chapter 8), while a sweep gives it a row. After launch a commit that is none of these is scope creep (v0.10.0 §12.7).
  • Surface move. A diff that adds, removes or changes a route, a table, a topic or a schema file as the seam classifiers see them, or that touches a path under hsdd/contract/ (§4.3).
  • Phase work. A commit that delivers a phase of the tree: the diff lies within what the phase's Scope says, and the commit is no later than the phase's sign-off (§4.3).
  • Claim. A sentence in the owning node's closure that the code can make false without moving the surface: a phase's Scope or Verification line; the node header's Purpose, Owns, Does not own and Isolation strategy; a node decision; the Guarantees of a contract the node produces; the Decision of an ADR the node is governed by (§4.3). A produced contract's Interface is surface, not claim.
  • Sweep class. The sweep's disposition for a candidate: log, phase, retro, intake or unplaced (§4.3, §4.4). Where this document says "class" about a commit, it means this; about a request, it means an intake class.
  • Sweep record. The management document of chapter 5.
  • Retro phase, backfill, delegated sign-off. As v0.10.0 §11.8, §12.7 and §10.2 define them.

#3. Before the Code: the manual Class

#3.1 The class

v0.10.0 §11.2's class table gains a row:

Class Means Routes to
manual after launch, a request that, as described, moves no route, schema, topic or table, stales no claim of the owning node's closure, and lands inside one node no skill, no record: the answer names the node and the commit trailer; the change ships on the implementation repository's main line and the sweep attributes it (chapter 4)

The tests are the sweep's surface and claim tests (§4.3), applied to the request as described instead of to a diff. "Make the preview's total larger" moves no surface and names nothing a Scope, Verification, Guarantee or header sentence says: manual. "Rename the fee line to charge" stales a Verification line that says "shows the fee line": local, a phase. "Add a preview endpoint" moves a route: local or cross-node with a contract bump, as before. When the request's description does not let the skill tell, the class is not manual: the phase is the safe answer, and the sweep can still find later that the diff stayed below the line.

#3.2 What intake answers

For a manual request the skill writes nothing under hsdd/. Its report names:

  • the node, found as v0.10.0 §11.2 finds a landing;
  • the trailer the commit must carry, HSDD-Node: {node-id}, which is how the answer reaches the sweep (§4.4);
  • that the change ships on the main line of the implementation repository and is attributed by /hsdd-intake sweep after it merges, by the developer or by a lead before the next checkpoint;
  • the one condition under which the answer is void: if, while making the change, the developer finds it moves a route, schema, topic or table, the request comes back through request mode before it merges.

An as-built landing is not promoted for a manual request: promotion waits for the first change request that needs a phase (v0.10.0 §6.4, §4.3 here). On that landing the second test is not applied, as §4.3 says of the sweep: only the surface decides. An open intake on the node does not change the answer: a manual change touches no plan and no contract, so request mode's collision rules have nothing to serialize and nothing to record, and the report names the open record so the developer expects the overlap.

#3.3 Why no record

Request mode's rule is "the record before the handoff", so that the routing is auditable (v0.10.0 §11.2). A manual request has no handoff to a skill, and the thing that would make it auditable, one record per font change, is the cost the lane exists to remove. The audit trail is the sweep row the commit will get, and the trailer carries intake's answer to it. A manual answer the developer never acts on leaves nothing behind, which is right: a request nobody made a change for was not a change. A manual answer whose commit never gets swept is caught by the checkpoint as an unswept range (chapter 8), the same as any other shipped commit.

#3.4 Under hsdd-auto

manual is not an unattended class. An hsdd-auto intake segment is done only when the record exists with its handoff block (v0.11.0 §9.2), and a judgement is never a stop (v0.11.0 §8.2), so an unattended run cannot leave a request out of the tree. v0.11.0 §12.1's unattended table for hsdd-intake gains one row: a request that would be class manual, disposition decide: route it local and record the decision, class judgement. The owner sees in the segment's review that the run paid for a phase the interactive answer would not have, and nothing in hsdd-auto's scripts changes. Automating the sweep under hsdd-auto is deferred (§11.2).

#3.5 Before launch

manual does not exist before launch. A request on an unlaunched system that is too small for its own phase is routed local and appended to the phase it fixes, or folded into an unshipped phase's Scope by the owner.

#4. The Sweep

#4.1 When it applies

A sweep applies to a launched system whose tree is current enough that the next change will read it: after adoption, after the launch campaign sealed, or after a seal (v0.12.0 §4.11). It is run by whoever merged the small changes, a developer at the end of the day or a lead before a checkpoint, over the same range with the same procedure; the record names who. It does not apply before launch, and it is not the way to deliver a request: a ticket, a PRD or an incident goes through request mode before the code is written. The sweep looks only backwards, at commits that exist on the main line.

#4.2 The range and the candidates

The sweep reads one implementation repository's main line from {from} to {to}: every commit reachable from {to} and not from {from}, side branches included, since a merge commit is set aside and the commits it brought in are where the change is. {to} defaults to the main line's head. {from} defaults to the {to} of the newest sweep record for that repository (§5.1); the first sweep of a repository must name it, and the record says it did. A --from that is neither the previous record's {to} nor an ancestor of it is refused: it would leave commits between the two records that no sweep reads and no default ever reaches. An ancestor is accepted, and the overlap is set aside as classified. The records of one repository are therefore contiguous by construction, and "the commits after the newest record's {to}" is the whole unswept set. Under the standalone-spec-repo profile each implementation repository is swept on its own, from that repository, and the records land in the submodule.

Of the commits in the range, the script sets aside, with a one-line listing each in the record:

Set aside Test
merge commits more than one parent
governance-only commits every changed path is under hsdd/, hsdd-context/ or openspec/
attributed commits the message's subject, body or a trailer names a phase id the tree's plan files define, as a whole token (not preceded or followed by a letter, a digit, _ or -, and not followed by . and a digit); a message naming an id no plan defines is not attributed, and the record notes the unknown id
commits a phase records a phase's Scope line cites the sha, at least seven characters, as a whole token: the retro phases of the legal bypass predate the commit's message, and their commits are recorded already; listed under attributed
classified commits a sweep record of this repository already lists the sha

Everything else is a candidate, and every candidate gets a row. The script never drops a candidate, and the agent never adds one. A range with no candidates writes no record: the report says so with the counts, and the next sweep's default {from} is unchanged.

#4.3 The tests

A candidate's class comes from three tests applied in order. The first is the script's, the other two the agent's.

The surface test (script). Over the commit's changed paths taken together, the script extracts routes, topics and migration tables from the content before and after the commit with the seam classifiers of hsdd-adopt's extractor, copied verbatim; a difference in any of the three is a surface move. A route or topic is compared by its method and path, or its direction and name, never by its file or line, so moving a handler between files or reformatting one is no move. A migration file added, changed or removed is a move whatever it says, since the classifier sees only CREATE TABLE and an ALTER TABLE changes a table too. So is a schema file (proto, OpenAPI, GraphQL, Avro, JSON Schema) added, changed or removed, and so is any changed path under hsdd/contract/. A candidate with a surface move is class intake, with the move as its reason (route added POST /payouts/preview, schema changed api/openapi.yaml). The classifiers are regex candidates, as hsdd-adopt says of them: a move they miss is for the agent to raise, and a diff that changes what a produced contract's Interface describes is such a move whether or not they saw it; a move they report is never lowered by an agent.

The phase test (agent), for every candidate, those the surface test set intake included. A commit with no phase id in its message may still be the work of a phase: only the convention of chapter 8 ties the two together. The agent reads the owning node's phases and their verification docs, nothing wider. The commit is phase work when a phase of its owning node, not dropped, describes it: the diff lies within what the phase's Scope says, and the commit's author date is no later than the date in the Sign-off of the phase's verification doc, when that doc is signed. On a row the surface test set intake, the phase must also account for the move, in its Scope or its Produces. The class is then phase, the reason is the phase id, and the row is the whole record of the commit: no claim test and no handoff, because the phase's own gate and verification doc answer for it. A commit that spans two nodes stays intake, since a phase belongs to one node. Sharing a node is not evidence: a small fix on a node with an open phase is not that phase's work. When the diff does not let the agent tell, it asks the runner once, and a commit nobody claims for a phase goes on to the claim test.

The claim test (agent), for every candidate the first two left. The agent reads the diff and the owning node's closure, nothing wider: the node's spec file, the Scope and Verification lines of its phases, the Guarantees of the contracts the node produces, and the Decision of each ADR in its Governed by. If the diff makes any sentence there false or stale, the class is retro, and the reason names the claim by its location (acme.web.checkout.4 Verification: "shows the fee line"). Otherwise the class is log, and the row is the whole record of the commit. A copy change that renames what a Verification line names is retro; a font size is log; a log line is log unless a Guarantee speaks of logging. The agent writes the claim it found, never a judgment of worth: "not worth recording" is not a class, and the question the agent answers is the bounded one.

On an as-built node (- **Adopted:** as-built, v0.10.0 §6.1) the claim test is not applied. Its header is an unvalidated claim about intent (v0.10.0 §6.5), its ## Observed surface is re-rendered by the checkpoint's drift pass, and it has no phases whose lines a diff could stale. A candidate placed on an as-built node is log unless the surface moved; a retro phase is never planned on an as-built node, and promotion waits for the first change request that needs a phase, as v0.10.0 §6.4 says. Depth on demand holds for small fixes too.

The agent may raise a class: log to retro, and either to intake when it reads a move the classifiers missed or when the paths span two nodes (§4.4). It never lowers one. Moving a script-set intake to phase is not lowering: the commit already has a phase, and that phase answers for the move. A person who runs the sweep may lower any class before the record is committed, the agent's or the script's, with a change-log line - YYYY-MM-DD: lowered {sha7} from {class} to {class} by {person}: {reason}; a script-set intake lowered this way records a false positive of the classifiers (a route-like string in a comment, a .schema.json fixture), and the record's Run by line is who answers for it. After publication no class is lowered (§5.3).

#4.4 Placement

Every candidate names the node it happened in, by this order of evidence:

  1. an HSDD-Node: trailer in the message naming an active node the tree defines, which is where a manual answer (§3.2) arrives; it is a hint and does not override spans;
  2. the script's proposal: exactly one node whose ## Observed surface modules: line (v0.10.0 §6.2) covers every changed path; when the modules: lines of two nodes each cover some of the paths, the script sets intake with the reason spans (below);
  3. the agent's reading of the atlas (hsdd/spec/ when there is none): each node's Isolation strategy, its phases' Scope lines, and any modules: line, the same prompt the user's guide gives;
  4. the person running the sweep, asked once, for the commits the first three left.

Paths that span two nodes make the commit intake with the reason spans {node}, {node}: two nodes is the first sign the change is not small, and the collision rules of v0.10.0 §11.7 belong to request mode. A commit whose paths are partly unowned is placed by the runner or not at all. A retro placed on an internal node or the root goes to the leaf-parent the runner names, and the claim test runs again there; when the runner names none, the row is unplaced. A commit no node owns and nobody places is unplaced, with the paths as its reason; it is listed for the owner (§6.3) and is never guessed onto a node.

#4.5 Who runs it, and who answers

A sweep's Run by line names a person, or {agent} for {person}, the same rule as a sign-off (v0.10.0 §10.2). The classification is a judgment and must be answerable. The next checkpoint lists sweep records run by delegation since the last one in the same finding as delegated sign-offs, for the person to ratify. A developer sweeping their own merged fixes answers for them; a lead sweeping the week's range answers for the classification, not for the code.

#5. The Sweep Record

#5.1 The file

hsdd/management/YYYY-MM-DD-sweep-{repo}-{to7}.md: the date of the run, the repository's name, and the first seven characters of {to}. {repo} is --repo when the invocation gives it; else the last path segment of the origin remote's URL without .git, which is the same on every developer's machine; else the basename of the top-level directory, and the header's Repository line says which. The name is lower-cased with every character that is not a letter or digit replaced by -. It is the key under which records chain (§4.2) and the checkpoint matches them (chapter 8), so it must not vary by clone. A name that contains progress, execution-plan, milestones, atlas or intake is refused with a request for --repo: the first four are words the reading aids read as a dated report, and intake would match the *-intake-* pattern request mode and the checkpoint read open intake records by. A sweep record is found by YYYY-MM-DD-sweep- at the start of its name, never by -sweep- anywhere, so an intake record whose slug contains the word stays an intake record. Like intake records (v0.10.0 §11.5) the record is dated, never superseded and outside the supersedes chain; records accumulate, one per repository per run. The newest record for a repository is the one with the latest date and, among records of one date, the one whose {to} descends from the others' on the main line.

Every cell is one clause. The Reason cell is none for log, the phase id for phase, the claim's location for retro, the surface move or the spanned nodes for intake, the paths for unplaced. The Subject cell is the commit's subject line with any pipe character replaced by a slash. A category under ## Not candidates with nothing in it reads none. ## Produced reads none until a product lands. The record cites and never defines (v0.10.0 §12.1): a reason names where a claim lives, not what the code now does; what the code now does is the retro phase's business.

#5.3 Edits after publication

A published record accepts the two edits of v0.10.0 §12.2, ticking Status and appending to the change log, and one more, named here as the milestone absorb is named there: a person may edit the Node and Class cells of an unplaced row, and its Reason with them, with a change-log line naming the person and the new class, and with the handoff the new class needs appended to ## Routing. Nothing else is edited in place; a wrong class on any other row is corrected by a change-log line, - YYYY-MM-DD: raised {sha7} from {class} to {class} by {person}: {reason}, and by the handoff it now needs, appended to ## Routing. The row's class is then the last such line's, over its cell, and a raise on a closed record sets Status back to open in the same edit, so the checkpoint walks it again. No class is lowered after publication, by anyone: lowering happens before the commit (§4.3), and a published intake row's commit went to request mode, whose record says what it found. check and commit gate the first publication only: a published edit is committed with git directly, since the first change-log line keeps the counts of the day it was written.

#5.4 Closure

A record closes when every retro and intake row, its class read as §5.3 says, has its product named in ## Produced (a phase id whose Scope cites the record and lists the sha; an intake record whose **Request:** names the sha) and no unplaced row remains. Products are listed one per line, - H{n}: {product}, replacing none. Closure means the commits are attributed, not that the retro phases are done: a retro phase's done-ness is its node's ledger's business and its intake's, and the sweep record does not track it twice. A record with only log and phase rows is written closed by the sweep itself, on the day it is created, with no change-log line beyond the first. Every other record is closed by hsdd-checkpoint (chapter 8), which appends the products and ticks the status; the sweep closes nothing it did not create closed.

#6. Handoffs

#6.1 retro: one phase per node per record

For each node with retro rows, ## Routing carries one handoff H{n} in three prompts, which the agent runs in order or hands to the person who will. The first appends the phase through hsdd-phase-plan append mode:

text
/hsdd-phase-plan {node} per hsdd/management/{record}: add one retro phase
for commits {sha}, {sha}. Scope lists each commit with the claim it staled
(the record's Reason cells); Verification states the behavior as the code
now has it; review tier gate-only; gate the node default. Plan nothing the
commits did not do. If a commit moved a route, schema, topic or table, stop
and say so: that is an intake, not a retro phase.

The second drains what the append emitted, usually nothing: /hsdd-reconcile {node}. The third writes the verification doc, with {phase-id} filled by the agent from the append's result:

text
Write hsdd/verify/{phase-id}.verification.md from
hsdd/templates/verification.md for the retro phase. Commands to run: the
node's gate. Observed: run it now, dated, and open with "Retroactive:
written after commits {sha}, {sha} shipped". Outstanding and Learnings per
the template. Sign-off: {agent} for {person} (delegated), tier gate-only.
Run the commands; do not invent an observation.

{person} is the record's Run by person, who answers for the sweep and so for its retro docs; the checkpoint lists the delegated sign-off for them to ratify like any other (v0.10.0 §10.2). The phase is named (retro), cites the record in its Scope (v0.10.0 §11.3 names the intake record the same way), and lists the shas. No phase context is written for it: the code exists. A retro phase is one phase per node per record however many commits it lists, and it is never split by commit. v0.10.0 §7.2's ceiling sizes the run and the review of work not yet done; a retro phase records work that is done, so the ceiling does not apply to it, and a commit list too long to read in one sitting is a sign the sweep ran too late, which the record's range shows. A retro phase is never planned on an as-built node (§4.3).

#6.2 intake: one request-mode run per commit

For each intake row, one handoff to request mode, with the prompt:

text
/hsdd-intake route {repo}@{sha} (commit): {subject}. Shipped {date} on the
main line; the sweep found {reason}; per hsdd/management/{record}.

{date} is the commit's date. commit is a new authority value (chapter 8): the request is the diff, already in production. Request mode classifies it as any other request, local, cross-node, new-capability or structural, never manual (the surface moved), reads the open intakes for collisions, writes its record and hands off; the phases it produces are retro phases, since the code shipped, and the contract bump it orders is the one the surface move already made in the code. The intake record's **Request:** line names {repo}@{sha}, which is how the checkpoint ties it back to the sweep record (§5.4), and joins the Sources of the nodes it governs like any request's path. commit is an authority of request mode only: hsdd-spec's root ## Sources list and hsdd-auto's authority enum are unchanged, since a sweep's handoffs run interactively (§11.2).

#6.3 unplaced: listed for the owner

An unplaced row has no handoff. The record lists it, the sweep's report names it, and the next checkpoint files it as a finding: code on no node is unadopted surface, and its plan step is hsdd-adopt on that surface (v0.10.0 §15.1's "one case worth calling out"), or a person placing the commit under §5.3. The record stays open until the row is placed.

#6.4 phase: no handoff

A phase row has no handoff. The phase it names is delivered by its own coding cycle and closed by its own verification doc; the row only attributes the commit, like a log row.

#7. The Mode

#7.1 Role and packaging

The sweep is hsdd-intake's second mode. SKILL.md gains the manual class in its class table and process (chapter 3), the unattended row of §3.4, and a short section that says when sweep mode applies, how it is selected (§7.2), and that its procedure is the file sweep.md beside SKILL.md, read only in sweep mode so that request-mode runs do not carry it. sweep.md tells the agent to run the script, to fill only the cells the script left, to apply the phase test and the claim test as §4.3 states them and no wider test, to ask the runner for placements the evidence did not give, to fix a record check refused and run check again, and never to commit a record check refused. Its quality gates and anti-rationalization table are its own.

The skill's scripts/ directory, new in this release, holds sweep.mjs and lib/, Node 20 or later, no dependency, and eight files copied verbatim and kept byte-identical by a test in this repository: from hsdd-adopt/scripts/, the classifiers routes.mjs, topics.mjs, migrations.mjs and schemas.mjs, and diff.mjs with walk.mjs, which parse a modules: line as the drift pass does; from hsdd-summary/scripts/, md.mjs and extract-plan.mjs, which read node and phase ids as the seal and the reading aids do. The sweep then agrees with every other reader about what a route, a scope and a phase id are. The directory is copied verbatim to hsdd/scripts/sweep/ under the bundled-script copy rule (v0.11.0 §4.3), named for the operation as hsdd/scripts/seams/ is. Request mode never runs it, which is the condition the amended scripts rule sets (§1.3).

#7.2 Selecting the mode

The first word of the skill's arguments selects it: sweep is sweep mode; route, a path, a URL, or a described request is request mode. The slash command stays a one-line delegator whose description names both. When the arguments name neither, and the text says the change already shipped ("I merged", "these commits", a sha or a range), the skill asks once which mode is meant, and never sweeps a request or routes a commit range without being told. A commit given to request mode is the commit authority (§6.2), one commit per request, and is how the sweep hands a surface move back.

#7.3 Invocation

From an implementation repository's root, the directory that holds hsdd/:

text
/hsdd-intake sweep [--from SHA] [--to REF] [--main BRANCH] [--repo NAME] [--run-by NAME] [--today YYYY-MM-DD]

node hsdd/scripts/sweep/sweep.mjs draft [--from SHA] [--to REF] [--main BRANCH] [--repo NAME] [--run-by NAME] [--today YYYY-MM-DD] [--write]
node hsdd/scripts/sweep/sweep.mjs check hsdd/management/DATE-sweep-REPO-SHA7.md
node hsdd/scripts/sweep/sweep.mjs commit hsdd/management/DATE-sweep-REPO-SHA7.md

The skill's arguments after sweep are the script's. A developer types it after merging; a lead types it before a checkpoint. An unattended sweep under hsdd-auto is deferred (§11.2).

#7.4 The steps

draft reads the range (§4.2), sets aside what §4.2 names, runs the surface test (§4.3) and the script's placement (§4.4 steps 1 and 2), and writes the record of §5.2 with every candidate row present: intake rows with their class and reason; other rows with Class and Reason as ?; every row with Node filled where the evidence gave one, none on a spans row, and ? otherwise. The header and the ## Not candidates section are complete, Run by is ? without --run-by, the first change-log line carries ? for the counts only the agent can know, and ## Routing and ## Produced read none. Without --write the draft is printed and nothing is written; an existing record for the same repository and {to} is never overwritten, and a record of the repository with a ? cell left refuses the draft until it is finished or deleted, since its rows would otherwise read as classified. A --from earlier than the previous record's {to} is accepted and the overlap lands under classified by; one later than it is refused (§4.2). A --to that is not on the main line, or a --from that is not an ancestor of --to, is refused before anything is read. The script reads the repository through git only; it never checks out, stashes or writes to the working tree: the before and after contents the classifiers read are materialized from git show into a temporary directory outside the repository, removed afterwards. A range with no candidates writes nothing (§4.2).

The agent then fills every ?: the node by §4.4 step 3, asking the runner (step 4) for what the tree does not answer; the class and reason by the phase test, then the claim test. It raises classes as §4.3 allows and lowers none. It fills the change-log line's counts and Run by, from the invocation or by asking the runner once. It writes ## Routing from the rows, one handoff per node with retro rows and one per intake row, with the prompts of chapter 6 verbatim, in table order, numbered H{n}, each headed **H{n}** ({class}, {node or sha}):, a retro handoff carrying the three prompts of §6.1. For a record whose rows are all log or phase it leaves ## Routing at none and ticks Status to closed with the record's date.

check reads the record back against a fresh draft of the range its header names, with the record under check left out of the classified set, and refuses, naming the row, when: a candidate has no row or a row has no candidate; a cell is still ?; a class is not one of the five; a retro or intake row's reason is none; a row the draft set intake is anything but phase and no change-log line names its sha as lowered by a person (§4.3); a phase row's reason is not a phase of the tree, is a dropped phase, or is a phase of another node, or the draft's row spans two nodes; a log or phase row's sha appears in a handoff; a retro or intake row has no handoff whose first prompt names its sha; a retro row's node is as-built, or internal, or the root, where append mode has no plan to write into; a node named is not in the tree, is retired on a log, phase or retro row, or is none on one; Run by is empty or a template placeholder; the first change-log line's counts disagree with the table; Status is closed on a record with a retro, intake or unplaced row, or open on a record with only log and phase rows. A prompt names a sha only at chapter 6's sha positions, commits {sha}, {sha} and {repo}@{sha}, read across line breaks: the record's own filename ends in {to7}, and a subject may quote any sha, so neither counts. check exits non-zero and writes nothing; the agent fixes the record and runs it again.

commit runs check, then commits the record alone with the message sweep: {repo} {from7}..{to7}; anything else staged stays staged. Under the profile the commit lands inside the submodule and the pointer is bumped in the implementation repository; the step refuses while the submodule's HEAD is detached (v0.10.0 §14.4 rule 1, as the seal does). It never pushes. Under the profile the runner pushes inside hsdd/ before pushing the implementation repository, as every governance edit is pushed, or the pointer names a commit no clone has. The agent then runs the handoffs of ## Routing in order, or hands the prompts to the person who will.

#10. Evidence (informative)

#10.1 What FT-4 and the manual lane showed

FT-4 (v0.12.0 §8.1) is the released system whose tree went stale because its developers fixed QA findings by hand faster than phases could be planned, and whose owner found the one-retro-phase-per-change repair more expensive than the work it recorded. The seal answered the recovery. The user's guide then described a manual lane as a project convention: a fix that moves no contract surface may ship before its phase exists, carries HSDD-Node and HSDD-Kind trailers, and gets a same-day retro phase with a retroactive verification doc. v0.12.0 §9.2 deferred promoting the lane to a rule until a project had run it for a release.

The owner's request of 2026-11-05 said why the lane as described would not be run: for a font size, a copy change or a log line, a retro phase and a verification doc are the ceremony the lane was meant to remove, only moved to the same day. The request proposed a file of commit shas and a skill to bulk-intake them, deciding per entry whether the change was worth recording. Three observations shaped what this document does with it:

Observation Rule
A hand-kept file of shas duplicates the git log, drifts from it, and costs an edit per fix, which is the friction the lane exists to remove. The input is a range on the main line; the previous record supplies the default start (§4.2).
"Worth recording" as an open judgment is the question the method cannot answer well in an agent; the dividing lines the guide already names are tests an agent can apply. Two tests, surface and claim, the first by script and the second bounded to the owning node's closure (§4.3).
The one-retro-phase-per-change shape failed in FT-4 by volume, not by kind: a phase is the right record for a change that staled a claim and the wrong one for a change that staled nothing. Three classes; log is one row; retro is one phase per node per record (§4.3, §6.1).

#10.2 Why a mode, not a skill

The first draft of this document made the sweep a fourteenth skill, hsdd-sweep, on the rules as written: scripts ship with a new skill only (v0.10.0 §16.3, §18.1), and one artifact gets one skill (§1.5). The owner asked what a developer would have to remember, and the question exposed a gap. A developer who asked intake first about a font-size change would have been given a local class and a phase; one who made the change and swept it would have been given one row. A lane that rewards skipping the question teaches developers to skip it. The fix is one door in both cases: intake answers "where does this go?" before the code with manual (chapter 3) and after the code with the sweep (chapter 4), using the same two tests on the request's description and on the diff.

Two rules bent to make room. The scripts rule's intent, that a proven path never grows a script dependency, survives in the amended wording: request mode runs no script (§1.3). The one-artifact rule already has hsdd-checkpoint's four views as a deliberate exception, and the sweep record is a routing record like the intake record, written by the skill whose job is routing. The cost accepted is a larger skill: sweep.md beside SKILL.md, read only in sweep mode, keeps request-mode runs from paying for it.

#10.3 What has not been shown

No project has run a sweep or received a manual answer. The claim test has not been measured for agreement between an agent and a person over a real week of commits, the surface classifiers have been exercised only on hsdd-adopt's fixtures, and whether developers ask intake first or sweep after is unknown. The first field run should record, in its records' change logs, every class a person lowered, since each is a case the agent judged too strictly, and every log row a later checkpoint found to have staled a claim, since each is a case it judged too loosely; and it should count the manual answers against the sweep rows that followed them. Chapter 11 marks every decision reasoned-only.

#10.4 What 0.13.1 corrected

The owner asked after the merge whether a sweep handles commits interleaved by developers working on different intakes. A throwaway repository showed that it handles the authors and not the intakes: five commits from three people landed on the right nodes, and two phase commits with no phase id read exactly like the small fix beside them. No review caught it, because every phase commit in the fixture named its id. The checkpoint had the same flaw, since 0.13.0 turned its judgment of "code with no phase" into a closed list.

A per-node maintenance ledger Derivable from the sweep records and git; a living appended file is a third in-place-edit model the management layer does not have. Written only if readers ask for it.
A verification doc field for external evidence Unchanged from v0.12.0 §9.2; a retro phase over several commits makes the field more useful, not less.
Sweep records on the reading aids The checkpoint page reads the progress report and plan; a sweep's effect is a line in the report's code-vs-plan section, which the page already renders. A sweep view waits for a release that touches the summary scripts.
A sweep across several repositories in one record One record per repository keeps the range, the default start and the closure per repository; a lead sweeping two repositories runs the command twice. Merged records return if that proves tiresome.
Reading sweep records at the seal A tree swept weekly does not go stale. If a sealed tree ever has open sweep records, the seal's close should close them too; the first such seal decides.
A minimal manual record Chapter 3 writes none. If the field shows developers want intake's answer on file before they commit, a one-line entry in the next sweep record's ## Not candidates, or a manual line in a running file, is the cheapest shape; the trailer serves until then.

#11.3 Rejected

  • A fourteenth skill. Drafted first on the rules as written, withdrawn for the entry-point argument of §10.2. The rules it honored are the owner's, and the owner amended one and read the other's existing exception.
  • A hand-kept file of commit shas as the input. It is a copy of the git log that can drift from it, and an edit per fix is the friction the lane removes. The curation it would carry lives in trailers and in the runner's answers.
  • A mode of hsdd-checkpoint. The checkpoint already finds unphased commits, but it is periodic, expensive and read-only toward governance; the sweep is event-driven, cheap, and must hand off into governance. FT-4's owner found the checkpoint's output more than a person reads; tying the cheap lane to it would make the lane unused.
  • An intake record for a manual request. One record per font change is the ceremony the class removes; the sweep row records the commit, and the trailer records intake's answer.
  • "Worth recording" as the agent's question. Unbounded, unauditable, and the kind of judgment the method keeps with people. The bounded tests are auditable by anyone who reads the row.
  • Not recording log commits at all. Then they are scope creep at every checkpoint, or the checkpoint must learn to ignore them, and the tree's attribution is incomplete in a way nobody can see. One row is the cheapest honest attribution.
  • A verification doc per log commit. The ceremony the lane exists to remove; a log row claims nothing a doc would verify.
  • One retro phase per commit. FT-4's repair shape; it fails by volume.
  • A required commit trailer. A commit without one still gets classified; a lane that requires discipline at commit time is the lane that gets skipped under pressure, which is when it matters. A manual answer asks for the trailer, and a commit that forgot it is placed by the other three steps of §4.4.
  • A living per-repository ledger instead of dated records. A third in-place-edit model; dated records follow the intake precedent, and the {to} in the name gives the next sweep its start without parsing.
  • Attributing a commit through the merge that brought it in. It needs a branch-name convention the method does not have: Merge pull request #16 from ... names no phase id, and acme.web.5-preview fails the boundary rule. It also misses trunk-based work. The phase test covers every case.
  • Guessing the mode. A request swept, or a range routed, is a wrong artifact written with confidence; one question costs less.

#12.1 Script tests

A dropped phase is read from its record. At least:

  • the set-aside: merges, governance-only commits (the gitlink included), attributed commits with the boundary rule, unknown ids noted, a commit a phase's Scope cites by sha under attributed.

  • placement: the trailer first, then a unique modules: match, then ?; both prefixes give intake with spans by script; no node gives ?, never a guess.
  • the as-built rule: the commit under the as-built node's prefix drafts with the node proposed; filled retro by a test, check refuses it; filled log, it passes.
