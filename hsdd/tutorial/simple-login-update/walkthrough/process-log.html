Process log: simple-login update 1 (phone number)

The record of one change to a finished HSDD project, from the change request to tested code, with the HSDD v0.10.1 skills as written in this repository's skills/. Times are WIB (UTC+7), 30 October 2026.

Every HSDD stop meant for a human (a ruling, a collision, a sign-off) was taken by Claude acting for the owner, by the owner's choice before the run. Each is marked [owner proxy]; the closing notes list them all.

#Starting point

  • template/ is docs/tutorial/simple-login/execute/ as it was merged (six phases shipped, every verification doc signed), plus one new input: hsdd/context/update-1-add-phone.md, an approved change request that amends AC-2.1 and adds AC-2.4 (show the phone number on Home).
  • execute/ started as a byte copy of template/ (12:55).
  • Baseline, 12:58: npm run install:all && npm test exit 0. Backend 70, replay 10, web 79 and the build, runner 3, browser 18. Ports 3000 and 5173 free afterwards.

#The flow the skills prescribe

A change to an existing tree enters through hsdd-intake, never through hsdd-spec at a new root ("a PRD is never a root"). The intake record classifies the change and names the next skill. For a cross-node change: hsdd-contract for the contract change, then hsdd-phase-plan in append mode on every node it lands on, then hsdd-reconcile, then the usual per-phase hsdd-config switch and coding method, then hsdd-checkpoint, which is the only skill that closes an intake record.

#Timeline

#12:59 · hsdd-intake: route the change

  • Read open intakes first. None: the project has no hsdd/management/ yet. No atlas either, so the landing was read from hsdd/spec/ directly, as the skill allows.
  • Landing. The phone number crosses the backend-to-web seam through profile-api: the backend owns the accounts and GET /api/me, the web owns Home, the integration node owns the browser test of every acceptance criterion. Three leaf-parents: class cross-node.
  • The contract decides the cost. profile-api@v1 is compatibility: versioned and its schema sets additionalProperties: false, so adding a field is breaking: the record routes to hsdd-contract for profile-api@v2 before any phase plan.
  • Record written before any handoff: hsdd/management/2026-10-30-intake-add-phone.md, with the five handoff prompts in order.
  • Finding (authority). The skill's authority values are accepted RFC, draft, ticket, incident, braindump. An approved PRD amendment, the most ordinary product change, is none of them; the record says ticket.

#13:02 · hsdd-contract and hsdd-adr: profile-api@v2

  • v2 is a separate file beside v1. hsdd/contract/profile-api.v2.md (id profile-api, version v2, draft, phase_ids: provisional), schema/profile-api.v2.schema.json, five fixtures under fixture/profile-api.v2/. v1's file, schema and fixtures are untouched: v1 stays stable until its consumers migrate. The registry generator projects both versions as two rows without change.
  • Checked, not assumed. v2's two 200 fixtures validate against the v2 schema and fail v1's (additionalProperties: false); the three 401 fixtures pass both and are byte copies. A phone without the international format is rejected by v2's pattern.
  • [owner proxy] v2 declares additive-only. Compatibility is declared per version, so drafting v2 forces the choice. v1's closed, versioned shape is why one display field cost a new version; under additive-only the next optional field amends v2 in place. The price is a new guarantee, "consumers ignore fields they do not know", which the web client already honors (it reads five named fields).
  • [owner proxy] One endpoint, one shape. GET /api/me cannot serve v1 and v2 side by side, and the PRD's "exactly two endpoints" rules out /api/v2/me. The migration note says so: the producer serves v2 only from its v2 phase on, the deprecation window is the gap between the producer's and the last consumer's v2 phases, and this intake ships them together.
  • v2 states its fixture format in full instead of "same shape as auth-api@v1's", as v1 did. Since v0.10.1 a cross-reference pulls the other contract into every phase context as referenced.
  • The bump ripples. Text that names profile-api@v1 was found in auth-api's token guarantee, ADR-001's affects, all three node specs and the root spec. Within this step: auth-api@v1 gets a compatible clarification (its guarantee names v2 too; version kept), and ADR-001's affects gains v2, as hsdd-adr's bidirectional-link rule requires once v2 says Governed by: [ADR-001]. Registries regenerated: three contract rows, one ADR row.
  • Finding (layout). hsdd-contract says a breaking change "creates v{n+1}" while "the old version remains stable", but names one file per slug ({slug}.md, {slug}.schema.json, fixture/{slug}/). Where two live versions sit is left to the run; this one chose a .v2 suffix on all three paths.
  • Finding (ripple). No skill lists what a version bump must update outside the contract. Node specs' Produces/Consumes and the root's contract matrix and DAG still say v1; they are left for the phase plans and reconcile, and logged where they are handled.

#Findings about HSDD's change flow

These came from running the v0.10.1 skills as written on a change to a finished tree. None blocked the run; each needed a judgment the skills do not make.

  1. Authority. hsdd-intake's authority values have none for an approved PRD amendment, the most ordinary change. Fixed in v0.10.2: approved PRD is an authority value.
  2. Two live versions. hsdd-contract keeps v{n} stable beside v{n+1} but names one file per slug. Where the second version's contract, schema and fixtures live is left to the run. Fixed in v0.10.2: a later version is a new file beside the first, {slug}.v{n}.md, with its schema and fixtures named the same way; nothing is renamed.
  3. The ripple has no owner. A bump leaves the node specs' Produces and Consumes, the root's copies, its contract matrix and its DAG naming the old version. Append mode may edit only Sources, no reconcile step names the edit, and no pending-entry type carries it: three planners each bent a note or a confirm sub-bullet to say so. Fixed in v0.10.2: append mode leaves the node header alone, and reconcile writes a confirmed version into the header and every copy above it.
  4. One endpoint, two versions. "The old version remains stable until every consumer migrates" assumes versions can coexist. At one endpoint they cannot: the deprecation window collapses to the intake, and v1 is stable with no producer until someone deprecates it (the checkpoint's F-1). Fixed in v0.10.2: the migration note names its mode; under lockstep the old version is deprecated at the bump, with its sunset when the new version's producer ships, and the checkpoint flags a stable version nothing serves.
  5. A migrated version never loses its consumers. v1's consumers will name web.1, web.3 and integration.1 forever; nothing removes a phase that migrated, so "no live consumer" cannot be read from frontmatter when retirement comes. Fixed in v0.10.2: the checkpoint reports migrated phases and reconcile moves them from consumers to former_consumers, so consumers means live.
  6. "The request's path". Append mode adds it to Sources; all three planners had to decide whether that meant the intake record or the change request (all chose the request). Fixed in v0.10.2: the change request's own path joins Sources; the intake record goes in the Scope.
  7. A pointer is not content. web.4's Scope said "per the request's Screen"; the context carried neither the Screen nor a link to it. hsdd-phase-plan already says binding details from a source belong in the Scope; nothing checks it. The first run's D{n} finding is the same family. Fixed in v0.10.2: hsdd-phase-plan states that the context carries no source text and checks that no line leans on a pointer, and hsdd-config now injects the node decisions a phase cites.
  8. The sizing floor in append mode fires on every small appended phase and has no partner to merge with, because the neighbour shipped; append mode could say what to record. Fixed in v0.10.2: in append mode the floor runs over the appended phases only.
  9. "On spec-repo main" decides shipped-ness and closure; on a project whose main line is a branch, the planners, the closure rule and the checkpoint each needed it ruled. Fixed in v0.10.2: conventions name the main line (**Main line:**, main when absent).
  10. referenced costs lines. v0.10.1's full-text rule put the old version into every migration phase's context (about 250 lines each, against 65 to 190 in the first run). Useful here; worth watching. No change in v0.10.2: kept, and watched.
  11. Red after a hard edge. An integration phase starts after its dependencies merged, so superpowers' "see it fail" needs an older tree to fail against. Fixed in v0.10.2: the context's test-first rule says to fail against the tree before the merged dependency, or against a named mutant.
  12. Who signs. The verification template says dispositions are made "by the human running the gate", but the checkpoint's audit checks only that the fields are filled; it counted proxy sign-offs as done and raised F-2 instead. Fixed in v0.10.2: a delegated sign-off names the person it answers to, counts as done, and goes to that person in one checkpoint finding to ratify; a sign-off that names no person leaves the phase a claim.
