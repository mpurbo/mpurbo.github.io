#1. What 0.11 Changes and Why

#1.1 The problem

HSDD planning is paced by its ask points. hsdd-spec stops on "who builds what?", hsdd-phase-plan stops on a structural contract gap, hsdd-reconcile stops on a collision or a breaking amendment, and a dozen softer questions (accept this ADR, answer this request) wait for a human between steps. For a tree of nine nodes that is a few hundred questions spread over days, and most of them have an answer the sources already imply.

An owner who wants the whole tree planned, or one change routed through every node it touches, can instead hand the run to an agent and review the decisions afterwards in one sitting. FT-3 did exactly that, twice, with an orchestrating Claude Code session driving one subagent per skill invocation. It worked: no step failed, every decision was recorded with its options and evidence, and the owner could audit the run step by step. It also showed what a hand-built orchestration costs and where it breaks (chapter 14): the protocol lived in a pasted prompt, the orchestrator wrote over a quarter of all output tokens restating context, timestamps were typed by hand and some were wrong, prompts carried facts from the orchestrator's memory, and the scripts that made it work lived in a session scratchpad that was later emptied.

#1.2 What this release adds

  • hsdd-auto, a twelfth skill (chapter 3). It owns the run: it computes the next step, renders the step's prompt from templates, dispatches one fresh subagent per step, answers stops as the owner's stand-in or ends the run, gates and commits each step, and keeps the records. Its scripts ship bundled and are copied verbatim into the project, like gen-registry.mjs and the seam extractor.
  • Run records (chapter 6): a decision ledger, a run log, the rendered prompt of every dispatch, a routing queue, step reports, and a report per segment. They are the input of a later judgement layer (§16.2).
  • Two modes (chapter 9): plan, which plans an empty tree through reconcile, and intake, which routes one change request into a planned tree through hsdd-intake and every handoff its record names.
  • A stop policy (chapter 8): the owner chooses per segment whether a stop condition ends the run with STOP.md or is decided and recorded with would_have_asked: true. Answers can be decided in advance per stop class.
  • An unattended-mode contract for six planning skills (§12.1): each skill lists its ask points as a table and, when invoked by hsdd-auto, returns a structured stop at an ask point instead of a question, and records each decision at the moment it takes it.
  • Three additive changes to existing skills (§12.2 to §12.4): an optional machine-readable handoff block in the intake record, a named align mode for hsdd-reconcile, and a rule for moving citations when a source document or contract version changes.
  • A Claude Code adapter (chapter 11): permission deny rules and a Bash hook that keep a run inside its declared inputs, installed into the project by hsdd-auto.

#1.3 What it does not change

  • The core invariant (v0.10.0 §1.3). hsdd-auto plans; it never implements a phase, never runs hsdd-config, and never passes a review gate.
  • Human review. Unattended planning moves the human's review from each ask point to one sitting over the ledger; it does not remove it. Every answer the run gave on the owner's behalf is listed first in the segment's report.
  • Artifact formats (v0.10.0 §15.3). Every change to an existing artifact is an optional addition whose absence keeps the artifact conformant. The formats this document introduces join the frozen set when v0.11.0 is released (§15.2).
  • The scripts boundary (v0.10.0 §16.3, §18.1). Scripts ship bundled with the new skill and change no existing skill's behavior. The existing skills change only through their own text (chapter 12), and only when invoked by hsdd-auto.
  • No scheduler, no CLI, no judge. Nothing starts a run on a timer; the one timed wait inside a run is §8.8's fallback wake-up. There is no hsdd command line. A judge that scores artifacts and gates steps is deferred (§16.2); this release records what it will need.

#1.4 Versions

v0.11.0 follows v0.10.2 as a minor release. The v1.0 release criterion (v0.10.0 chapter 17, the published case study) is unchanged.

#1.5 How to read this document

Chapters 2 to 13 and the appendices are normative. Chapter 14 is the evidence the design rests on and is informative. Chapter 15 states compatibility, chapter 16 the decisions and what is deferred, chapter 17 the acceptance criteria. Must and never are requirements; should is a default a project may override in its run configuration. A section number without a version prefix refers to this document; v0.10.0's sections are written "v0.10.0 §n", and a list that follows that prefix stays in v0.10.0 ("v0.10.0 §16.3, §18.1"). The prefix names the v0.10 document, spec/hsdd-spec-v0_10.md, as of 0.10.2: 0.10.1 and 0.10.2 edited it in place without renumbering a section, so "v0.10.0 §n" reads that section's 0.10.2 text.

#2. Vocabulary

These terms are used with exactly these meanings throughout. v0.10.0's chapter 19 gains them (§15.4).

  • Run: one unattended effort on one branch of one repository, configured by one run configuration (hsdd/auto/run.yaml). A run has one or more segments and lasts until the owner merges or abandons its branch.
  • Segment: a stretch of unattended work opened by one owner instruction: the first /hsdd-auto, a later /hsdd-auto intake <source>, or the answer to a STOP.md. Each segment has one mode, one stop policy, one preamble version and one report, or a share of the next segment's when it ended early (§10.9). Steps are numbered across the whole run, not per segment.
  • Step: one unit of work with an id (S00, S01, ... S100), a kind, a target, a write set, and two commits. A subagent step is exactly one HSDD skill invocation on one target by one fresh subagent. An orchestrator step (setup, plan, report) is done by the orchestrator itself and runs no HSDD skill.
  • Step kind: the type of a step, which fixes its skill, its template, its write set and the decision type of the decisions taken in it (§7.1).
  • Launch: one start of a step subagent: the initial dispatch, a re-dispatch after an interruption, or a resume (§8.6).
  • Continuation: a new step of the same kind and target as a step that ended stopped, dispatched once the stop is resolved (§8.3).
  • Owner: the human who configured the run and reviews it. The only source of instructions. Facts the owner states are owner facts.
  • Orchestrator: the agent session that runs hsdd-auto. It sequences steps, launches subagents, answers stops as the owner's stand-in, reviews each step, runs the scripts that gate, commit and record, and writes the change log and the report's prose. It never runs an HSDD planning skill in its own context.
  • Step subagent: a fresh agent with no context except its dispatch file. It invokes one HSDD skill, writes that skill's artifacts, its experiments and its step report, and records its decisions. It never commits and never answers a stop.
  • Decision: a choice between at least two options that a human could have made, recorded with its options and consequences, the chosen option, the reason, the evidence, the blast radius and the confidence (§6.2).
  • Decision ledger: hsdd/judgement/decisions.jsonl, one decision per line, append-only, each line pinned to the commit holding the artifact it landed in.
  • Run log: hsdd/judgement/run.jsonl, one line per step.
  • Stop: a point where the run cannot proceed without an owner's answer. A skill stop is one a skill's ask-point table marks return (§12.1). A run-stop candidate is a stop-set condition a subagent meets outside a skill stop. Every stop has a stop class (§8.2).
  • Stop set: the stop classes that end the run under the stop policy.
  • Stop policy: per segment, stop (a stop in the stop set writes STOP.md and ends the run) or decide-and-record (the orchestrator answers it and records it with would_have_asked: true).
  • Predecided answer: an answer fixed before any step met the stop, keyed by stop class, injected into every prompt (§8.4).
  • would_have_asked: a decision field: true when a skill stopped for a human, or a careful engineer would have put the question to the owner first.
  • would_upstream: a decision field: true when the right resolution is a change to a read-only source; the decision is resolved locally and listed for upstreaming.
  • Blast radius: what a decision can change. node-local: one node's internals. contract: a contract's interface or guarantees, so every consumer. tree: which nodes or contracts exist. upstream: a read-only source would change.
  • Routed item: a follow-up one step raises for a later step, kept in the routing queue hsdd/auto/queue.jsonl (§6.5).
  • Write set: the paths a step may change (§7.3).
  • Judgement set: the run's record files a step's judgement commit holds (§6.11).
  • Gate: gate.mjs, the mechanical check of a step before its artifact commit (§10.6).
  • Experiment: a throwaway program a subagent writes and runs to settle a runtime fact a decision depends on, kept with its captured output and cited as evidence (§7.5).
  • Owner files: paths the owner names that no step may change, guarded by hash (§6.10).
  • Out-of-bounds paths: paths no agent in the run may read (§5.1, chapter 11).
  • Sources: the documents the project implements. Normative sources bind; informative sources guide; baseline sources are an earlier version, read only to see what changed.
  • Segment report: the document the owner reads first, written at the end of each segment (§10.9).

#3. The Skill

#3.1 Role

hsdd-auto is a role skill like the other eleven: one artifact class (the run and its records), one skill. Its row in v0.10.0 §1.5's table:

Skill Role Key outputs
hsdd-auto Run HSDD's planning chain unattended: compute the next step, dispatch one fresh subagent per skill invocation, answer or stop on each ask point per the owner's stop policy, gate and commit each step, and record every decision for one review sitting. hsdd/auto/, hsdd/judgement/, a report per segment

It drives six of the existing skills: hsdd-spec, hsdd-adr, hsdd-contract, hsdd-phase-plan, hsdd-reconcile and hsdd-intake. It never drives hsdd-adopt (adoption's human confirmation is the owner's, v0.10.0 §6.4, §6.5), hsdd-config (execution), hsdd-checkpoint, hsdd-milestone or hsdd-summary.

#3.2 Packaging

The skill is a SKILL.md that the orchestrating session follows, plus zero-dependency Node.js scripts that do every part of the work that has one right answer: which step is next, what its prompt says, what it may write, whether it passed, the commits, the records, the timestamps. The model is used only where judgement is needed (§3.4). A Claude Code adapter (chapter 11) adds enforcement at the edges; the skill and its scripts work without it on any agent host that can launch a subagent with a prompt and read its result.

A Claude Code plugin as the package was rejected (§16.3): tool-level enforcement, but one host only. An external runner on an agent SDK is deferred (§16.2): deterministic sequencing, but every judgement point then needs its own model call, which is building the judge first.

#3.3 Invocation

text
/hsdd-auto                          start a run, or resume the current segment
/hsdd-auto intake <source> [flags]  open an intake segment for one change request
/hsdd-auto status                   where the run is: segment, last step, next step, open queue, stop

Flags: --stop-policy stop|decide-and-record overrides the opening segment's policy; for an intake, --authority accepted-rfc|approved-prd|draft|ticket|incident|braindump gives the request's authority (default draft), from v0.10.0 §11.2's list; an approved amendment to a PRD is approved-prd, as hsdd-intake says. Prompts and records render an authority in hsdd-intake's words, through one map for every value: accepted-rfc as "accepted RFC", approved-prd as "approved PRD", the others as written. So the intake record's **Request:** line, and the root's ## Sources entry that hsdd-reconcile copies from it, carry those words.

The slash command is a one-line delegator, commands/hsdd-auto.md, like every other skill's (v0.10.0 §14.3).

The only interactive moment is the first /hsdd-auto in a project with no hsdd/auto/run.yaml: the skill asks the questions of §5.3 once, writes the file, shows it, and starts. Every later invocation reads the file and asks nothing. An owner's words in the invoking message that bear on the run ("do not ask me anything", "treat v2 as normative") are read by the orchestrator and recorded as setup decisions of the segment they open (§8.1); they are never applied silently.

#3.5 Where it runs

From the repository that holds the tree at hsdd/ (v0.10.0 §9.5), on a branch the run creates from a base branch and commits to under v0.10.0 §9.4's branch discipline. Steps run serially (§16.2 defers parallel dispatch). The standalone-spec-repo profile (v0.10.0 §14.4), where hsdd/ is a submodule, is not supported in v0.11: /hsdd-auto refuses to start when hsdd/conventions.md declares it, and says so (§16.2).

#4.3 Bundled-script copy rule

The skill's scripts/ directory is copied verbatim to hsdd/scripts/auto/, the same rule as hsdd/scripts/summary/ and hsdd/scripts/seams/. The copy is current when its VERSION equals the installed skill's and every file is byte-identical; anything else is a gate error (§10.6, A3), fixed by recopying in a setup step or, mid-segment, in a plan step by a recorded decision (§7.3), never by editing. Until the first setup step has made the copy, the orchestrator runs the scripts from the installed skill's scripts/ directory.

#4.4 What SKILL.md contains

The skill text follows the house shape of the other skills: front matter with a description, triggers and "Do NOT use for" lines, then:

  1. Preconditions: run from the repository holding hsdd/; not the standalone-spec-repo profile; a clean working tree apart from the declared owner files; the six planning skills installed with their ## Unattended runs sections (§12.1); Node.js 20 or later on the path.
  2. First run: the questions of §5.3, run.yaml, the bundled-script copy, the adapter (chapter 11), the branch, the setup and plan steps.
  3. The loop of chapter 8, as numbered steps naming the script to run at each point.
  4. Judgement points: answering a stop (§8.3), deciding in advance (§8.4), accepting an inserted step (§8.7), reviewing a step (§8.5), reading an owner instruction (§8.1, §8.11). Each says what to record.
  5. Context recovery (§8.9).
  6. Finishing a segment (§8.10).
  7. Quality gates, as checkboxes: two commits per step; every decision minted and stamped by decide.mjs; no prompt fact that was not read from a file by dispatch.mjs or cited to one; no step id reused or renumbered; no STOP.md under decide-and-record except for §8.2's hard stops.
  8. Anti-rationalization table, at least: "I remember what that step decided, I'll restate it in the prompt" (facts come from files); "the timestamp doesn't matter, I'll write one" (only scripts stamp); "this stop is obviously answered, I'll let the subagent take it" (a stop is the orchestrator's, recorded); "the gate is wrong this once, I'll commit anyway" (fix the step or the configuration by a recorded decision, never bypass); "I'll check on the subagent in a few minutes" (wait for the hand-back).

#5. The Run Configuration

#5.1 Fields

hsdd/auto/run.yaml holds everything about a run that is the owner's to say. The orchestrator edits it only in a setup step, by a recorded decision, except that a plan step may add a predecided entry (§8.4). Its JSON Schema is appendix A.1.

#5.2 The YAML subset

run.yaml is written by people, so it is YAML, and the scripts parse it without a dependency, so it is a subset. lib/yaml.mjs accepts exactly: block mappings; block sequences; flow sequences whose items are scalars or flow mappings ([a, b], [{path: x, cite: Spec}]); flow mappings of scalars ({path: x, cite: Spec}); plain, single-quoted and double-quoted scalars on one line; integers; true, false, null; and # comments. Double-quoted scalars accept the escapes \", \\, \n, \t and \uXXXX. Indentation is spaces only. Anything else (anchors, aliases, tags, multi-line scalars, multiple documents, tabs) is a parse error that names the line. Writers quote any string containing : , #, a leading special character, or a value that would otherwise read as a number or boolean. lib/yaml.mjs also writes the subset, so state.mjs open-segment can append a segment entry without disturbing the owner's comments: it appends the entry's line under segments: and rewrites nothing else. A first-run file writes segments: with no value, which the loader reads as an empty list (as it reads []), and the appender replaces that line with the block sequence.

#5.3 The first-run questions

When run.yaml is missing, /hsdd-auto asks these, in one batch, proposing a default for each from what it can read (the root spec's ## Sources, hsdd/conventions.md, git status, the owner's agent instruction files):

  1. The run's name (default: the repository directory's name), the root node id (default: the run's name), the branch (default auto/{run}), the base (default the current branch), and where the HSDD skills are installed (default: the first of .agents/skills, .claude/skills, ~/.claude/skills that holds hsdd-auto).
  2. Who builds what: one team or several, and the team per subtree. The answer becomes an owner fact, so the axis stop never fires. The owner may answer "decide": the skill then removes axis from stop_set, and the root step decides the axis and records it with would_have_asked: true and class axis.
  3. The sources: which documents are normative, informative or baseline, their citation names and versions.
  4. Read-only paths and out-of-bounds paths.
  5. Owner facts: anything the run must take as given (coding method, tooling the run may not install).
  6. Toolchain command prefixes and rules.
  7. Stop policy and stop set, with the defaults shown.
  8. Owner files: default every path git status shows as modified or untracked at that moment.
  9. Prose rules: proposed from the owner's instruction files when they state banned characters or phrases.
  10. Commit trailers.

The skill writes the answers to run.yaml, shows the file, and opens the first segment. A later /hsdd-auto never asks again; a configuration change is a setup decision of a new segment (§8.1).

#5.5 Segment entries

Each segments entry has:

  • id: {YYYY-MM-DD}-plan for a plan segment; {YYYY-MM-DD}-intake-{slug} for an intake, where {slug} is the request's file name without its extension (or a URL's last path segment), lower-cased, with every run of characters outside a-z0-9 turned into one -, cut at 40 characters, then trimmed of -; an empty result becomes request. When the id is taken, -2, -3 and so on are appended. The segment id is the run's name for the segment; the intake record's own slug is hsdd-intake's to choose and need not match.
  • mode: plan or intake. A segment opened by an answer to STOP.md has the stopped segment's mode.
  • opened_at: the time the skill started handling the owner's instruction, taken by the script that appends the entry, never typed.
  • instruction: the owner's words that opened the segment, verbatim: the message to /hsdd-auto, or for a bare first run the sentence the skill shows after the §5.3 questions and the owner confirms.
  • stop_policy, first_step: the next free step id when the entry is appended; dispatch.mjs --next for the segment's setup step allocates exactly this id and refuses otherwise (§7.2).
  • For an intake: request (path or URL) and authority. A segment opened by an answer to STOP.md or by an owner message (§8.11) copies the ended segment's mode, request and authority.

state.mjs open-segment (§10.1) appends the entry before the segment's setup step, computing the id, first_step and opened_at; that step's artifact commit carries it.

#6. Run Records

#6.1 Rules for every record

  • Append-only. No line of decisions.jsonl, run.jsonl, queue.jsonl, handoffs.jsonl or a decisions sidecar is edited or removed. A correction is a new line: a plan decision, or a queue line with the same id and a new status.
  • Times are taken, never typed. Every timestamp in a record is UTC at second precision with a Z suffix (2026-10-20T16:04:30Z), produced by a script at the moment the event happens: decide.mjs for a decision, dispatch.mjs for a step's start and each launch, commit.mjs for a step's end and a skip, routed.mjs for a queue event, state.mjs open-segment for a segment's opened_at. An agent never writes a timestamp by hand.
  • Paths are repository-relative with / separators, never absolute.
  • Validation by hand. Every script validates what it writes against the JSON Schemas of appendix A with lib/schema.mjs, which implements the subset those schemas use: type (a name or a list of names), enum, pattern, required, properties, additionalProperties (false or a schema), items, minItems, minLength, minimum, and $ref to #/$defs/{name} or to {file}.schema.json#/$defs/{name} in the same schema/ directory. No JSON Schema library is needed. Rules the subset cannot state are listed under each schema and checked in code.

#6.5 The routing queue

hsdd/auto/queue.jsonl, one line per item event, written only by routed.mjs. Schema: appendix A.5.

An item is opened from a report's routed entry (routed.mjs ingest) or by the orchestrator (routed.mjs open): {id: "Q-001", at, status: "open", from, target, kind, text}, with step_kind and step_target for an insert-step item. Its kind:

  • must-address: the target's next step must do it or explain why not. An open must-address item fails the final gate.
  • consider: the target's next step must read it and say what it did. An item still open at the segment's end is listed among the report's deferred findings.
  • insert-step: proposes a new step of step_kind (any subagent kind except intake) on step_target, for the reason in text. Its target is always run, so it never matches a step. An optional after names an intake handoff id, or handoffs for all of them, that must be executed or skipped before the step runs (§8.7). The orchestrator accepts or rejects it with a plan decision (§8.7).

Targets are written as: a node id (acme.backend.auth), a contract slug without version (auth-token, the contract's id, which stands for every version file of it), the file name of one later version without .md (auth-token.v2, v0.10.0 §3.1), an ADR id (ADR-003), an intake handoff id (H7a), or run (the run itself). A step's target string is its node id, contract slug or ADR id; for citation-touch, the touched file's node id, slug or ADR id; for reconcile and align, a comma-separated list of node ids, or all for every leaf-parent (for records and matching only: the skill drains every pending section in the tree, §7.1); for intake, the request path. An item matches a step when its target equals the step's target, is an element of the step's target list (all matching every leaf-parent), or is the handoff id the step executes. Once that handoff is executed or skipped, an item on its id also matches a step on the handoff's own target, so an item routed to a skipped handoff, or after its step ran, can still close (§9.1 stage 7); before then it waits for the handoff's step, and no other step on that target takes it. dispatch.mjs lists every open matching item in the step's prompt, and the step must close each in closes.

Closing. An item's later events are new lines with its id: addressed or explained (with by, the closing step, and note), written by routed.mjs ingest from a report's closes or by the orchestrator with routed.mjs close for items targeting run or the request path; accepted or rejected (with decision) for an insert-step item; and addressed for an accepted insert-step item, written by commit.mjs when the inserted step commits as completed (a stopped inserted step keeps the item accepted, and its continuation carries the item, §8.3). An item's state is its last line.

hsdd/auto/dispatch/{step}.md, written by dispatch.mjs when the step starts and committed in its judgement commit. It is the exact prompt the subagent received, so a step can be audited and re-run from it. Front matter (schema: appendix A.8):

The body is the rendered preamble (appendix B) followed by the rendered step section (appendix C). Each later launch appends to launches (redispatch, resume-answer or resume-finding) and, for a resume, a ## Resume {n} section with its message to the body. An orchestrator step (setup, plan, report) also gets a dispatch file, with skill: none, no report, and an empty body without a read check, so that every step has an id, a start time, a write set and a head recorded the same way.

The read check. A subagent step's body ends with the line read_check: {value}, where the value is eight hex digits from a cryptographic random source. It stays the file's last line: dispatch.mjs moves it below every section it appends. A redispatch draws a new value, since a fresh subagent must show its own read; a resume keeps it, since the message goes to the subagent that already read the file. The value is not in the front matter, so a read that stops short of the end cannot find it. Every report of the step echoes it (appendix A.4), and the gate compares the latest report's value with the file's (§10.6, B5). The file's size is bounded so that one read returns all of it (§10.3).

#6.7 STOP.md

Written by the orchestrator when a stop in the stop set fires under the stop policy, or a hard stop fires (§8.2), and committed in the stopped step's judgement commit. Shape:

markdown
# Run stopped at {step}

- **Segment:** {segment id}
- **Stop class:** {class}
- **Step:** {step} ({kind}, {skill} on {target})

## Question
{verbatim}

## Options
- **{label}** (recommended): {consequence}
- **{label}**: {consequence}

## What it blocks
{the steps that cannot run, by kind and target}

## How to resume
Answer in one message, then run `/hsdd-auto`. The answer opens a new segment
and is recorded as its owner's decision. For a stopped subagent step a
continuation of the same kind and target is dispatched with it; for a stopped
`plan` step the new segment's `plan` step turns the answer into steps (§8.3).

While STOP.md exists and no segment entry newer than the stopped step's has been appended, next.mjs returns blocked. The next /hsdd-auto must carry the owner's answer; the new segment's setup records it with decide.mjs --by owner --type setup, removes STOP.md, and the run continues with the continuation (§8.3).

#6.8 The owner's review line

hsdd/judgement/decision-reviews.jsonl, written by the owner, never by the run. Schema: appendix A.6. Fields: decision, at, review (agree, disagree, should-have-asked), reason (required for disagree and should-have-asked), and optionally reviewer, preferred (on disagree, the label the owner would have chosen, or other: {one line}) and impact (on disagree, the blast radius of the difference). A second review of the same decision is a new line.

#6.9 The plan

hsdd/auto/plan.md is the run's human-readable path, in three sections:

  • ## Segments: one paragraph per segment, written by the orchestrator in the segment's plan step: the mode, the owner's instruction, the stop policy, the stages next.mjs --stages printed, and the decisions the orchestrator expects to take. The first sentence of each paragraph states the segment's purpose in one line; the preamble quotes it (appendix B).
  • ## Step log: a table regenerated whole by commit.mjs from run.jsonl and handoffs.jsonl at every judgement commit: step, segment, kind, skill, target, status, artifact commit, and a row per skipped handoff. Never edited by hand.
  • ## Change log: entries appended by the orchestrator, saying what changed in the path and why (an inserted or rejected step, a skipped handoff, a configuration change, a continuation). Each entry opens with the id of the decision that made the change, whose at is the entry's time; no date is typed.

#6.10 The owner-file snapshot

hsdd/auto/owner-files.json maps each path in owner_files to the sha256 of its bytes, or null when it is absent (schema: appendix A.9). Each segment's setup step takes it. The gate fails a step when any hash differs (A2). The owner changing a file between segments is expected: the next segment's setup takes a new snapshot.

#6.12 Skipped handoffs

#7.4 Read sets

A step reads what its skill reads, its dispatch file, the sources, and its experiments. "What its skill reads" is the files the step section's fact lines name and the files the skill's own process steps tell it to open; a file outside both is a read outside. Two limits are stated in every prompt and checked through the report's reads_outside:

  • Sibling isolation (v0.10.0 §8.3). A phase-plan or phase-plan-append step must not read another node's ## Phase Plan section or pending section. Because a node's plan lives in its spec file, which the step may read for purpose and contracts, no path rule can enforce this; the template tells the step to follow its skill's own phase templates for format (appendix C), so it never needs a sibling's plan.
  • Out of bounds. No agent reads an out_of_bounds path. The adapter enforces it where the host allows (chapter 11).

A subagent that read outside its read set says so in reads_outside. The orchestrator records each entry as a plan decision (keep the step's output, or rework it) and the report lists it under record gaps.

#7.5 Experiments

When a decision depends on a runtime fact (what a library does, how a runtime schedules, what a parser accepts), the subagent writes a throwaway program under {experiments_dir}/{name}/, runs it with the toolchain's command prefixes, keeps the source and the captured output (output.txt, or output-{case}.txt), adds a README.md of at most ten lines whose first line is the finding, and cites the directory in the decision's evidence. An experiment never joins the project's build or workspace. A fact that a short program settles is never guessed.

#7.6 Prose rules and template tokens

The preamble passes prose_rules to every step. When a banned character is one an HSDD template uses as a token, the step writes the configured token_forms instead: empty_cell for an empty table cell or list, id_separator between an id and its title in a heading, and reason_separator before a Collides with reason, and source_separator between the path, authority and scope of a root ## Sources line. The forms must be among those v0.10.0's formats admit after §15.3's amendment: :, an en dash or - between an id and its title, - before a Collides with reason and in a ## Sources line, and none or - for an empty cell; hsdd-summary's plan extractor already reads each of them as it reads the em dash. The gate reports violations in write-set files at prose_rules.level (D1). Exempt: step reports, sidecars and the generated parts of a segment report, since they quote skill and decision text verbatim; H/conventions.md, a copied skill template whose prose the step does not rewrite; and the bundled copies under H/scripts/ and .claude/, which are never edited (§4.3). A segment report's prose slots are checked.

#8. The Loop

#8.1 Opening a segment

/hsdd-auto (or /hsdd-auto intake <source>) does, in order:

  1. Read the configuration. When hsdd/auto/run.yaml is missing, ask the questions of §5.3 and write it.
  2. Refuse when it cannot run at all. hsdd/conventions.md declares the standalone-spec-repo profile, or one of the six planning skills under skills_dir lacks its ## Unattended runs section (reinstall HSDD 0.11). The refusal says what to do and changes nothing.
  3. Read the state (state.mjs). If a step is in progress, or the current segment is unfinished, resume (§8.9) and skip the rest of this list: a new segment opens only when the current one is finished, stopped, or ended by an owner message (§8.11), and /hsdd-auto intake on an unfinished segment is refused with that reason. If STOP.md exists, the invoking message must carry the owner's answer, unless the newest segment entry has no setup commit yet (a crash after item 4), whose instruction then is the answer; otherwise refuse and show STOP.md's question. Before opening a new segment, refuse when the working tree has changes outside owner_files, hsdd/auto/run.yaml (a first run has just written it) and the judgement set.
  4. Open the segment with state.mjs open-segment (§10.1): it checks out the run branch, creating it from base when it does not exist, so that every dispatch file's head and every commit are on it, and appends the segment entry (§5.5).
  5. Run the setup step. dispatch.mjs --next starts it. Copy the scripts when the copy is not current (§4.3), copy gen-registry.mjs from hsdd-contract when contracts exist and the copy is missing or differs, take the owner-file snapshot, and install or check the adapter (chapter 11). Then record, with decide.mjs --by orchestrator:
    • the reading of each sentence of the owner's instruction that changes how the run behaves (which source is normative, the stop policy, a scope limit), with the sentence quoted as evidence;
    • the segment's stop policy when it differs from run.yaml's default;
    • each predecided answer (§8.4);
    • each change to run.yaml or an orchestrator_files path, made in this step;
    • an owner's answer to STOP.md, with --by owner, its evidence naming the stopped step's id; remove STOP.md; and when the answer is one an owner fact can carry (an axis answer), append it to owner_facts, so the continuation's skill finds it answered, recording the run.yaml change. Commit with commit.mjs --step {step} --status completed.
  6. Run the plan step. next.mjs --stages prints the stages the mode will walk (chapter 9) and which are done. The orchestrator writes the segment's paragraph under ## Segments in plan.md and records, as plan decisions, any choice about the path the stages leave open. Commit.
  7. Enter the step loop: repeat next.mjs, act on its result (§10.2), until it returns done or blocked; stop, close, decide and stuck are handled in a plan step and the loop continues.

For each subagent step the loop is: dispatch.mjs --next writes the dispatch file and prints the launch prompt; the orchestrator launches the step agent with it and waits (§8.8); on the hand-back it reads the report; it handles a stop (§8.3) or reviews the step (§8.5); then commit.mjs --step {step} --status completed.

gate-twice End the run with STOP.md (§8.3, case A). The orchestrator records the decision, commits the step as stopped, and a continuation with a fresh subagent receives the findings (§8.6).

A step that returns upstream or judgement as a stop is resumed with dispatch.mjs --resume {step} --reason finding --message-file {file} and the instruction to decide it; the orchestrator records no decision of its own, and the resume does not count against rework_limit.

Hard stops write STOP.md under either policy: an external need with no in-repository alternative; a continuation that itself reaches gate-twice (§8.6); a dispatch file that stays over the size limit once the orchestrator's context is shortened (§10.3); an owner file a step changed, which only the owner can restore (§10.7); and a stuck segment that no step kind can fix (§8.10).

#8.3 Answering a stop

A step subagent never answers a stop. It ends its launch with status: stopped (a skill stop) or status: run-stop-candidate (a stop-set condition met outside a skill stop) and a stop object (§6.4). The orchestrator then:

  1. Checks the read. It runs gate.mjs --step {step} --check B1,B5. An error means the subagent did not read its dispatch file to the end, where the predecided answers are, so the stop may be one they answer. The orchestrator resumes the subagent with that finding (§8.6) and handles nothing else until a report passes.
  2. Checks the class. It may correct the subagent's stop_class and says why in its decision.
  3. Checks the condition. For shape, the condition holds only when both options are defensible, they differ in nodes or contracts, and neither the sources, the owner facts, HSDD's rules nor an experiment gives one a stated reason to lead. When one has a stated reason, the condition does not hold: the orchestrator answers it (case B), cites that reason, and records would_have_asked: false.
  4. Ingests the report's routed items (routed.mjs ingest --step {step}) and accepts or rejects each insert-step item among them with a plan decision in this step's sidecar, as §8.5 does for a completed step; this happens before any commit.mjs --status stopped below.
  5. Handles it by §8.2's table, in one of three cases:
  • Case A: end the run. The orchestrator writes STOP.md (§6.7) with its recommendation, then runs commit.mjs --step {step} --status stopped, which commits the partial artifacts (gate checks A1 to A4, B1 and B5) and the judgement set with STOP.md. The run ends with a clean tree. The owner's answer later opens a new segment, and next.mjs returns the continuation.
  • Case B: answer and resume. The orchestrator records its answer in the step's sidecar (decide.mjs --step {step} --by orchestrator, with would_have_asked: true and the class, the subagent's options plus any it adds, and a why for the owner reading cold that names the signal that would have changed it). An answer to a breaking-amend stop names the migration mode, as a predecided one does (§8.4). It resumes the same subagent with dispatch.mjs --resume {step} --reason answer --message-file {file}, whose message gives the answer and the decision id. The step continues; nothing is committed in between. When the host cannot resume a subagent, the orchestrator instead commits the step as stopped and the continuation carries the answer.
  • Case C: supply the missing input. For procedural, the orchestrator records a plan decision in the step's sidecar, accepts the insert-step item the report routed for the step that supplies the input, or opens one when the report did not (routed.mjs open --from {step} --kind insert-step ...), citing that decision (routed.mjs decide), and only then commits the step as stopped, so the decision and the queue events land in the same judgement commit. next.mjs returns the inserted step, then the continuation.

Continuations. next.mjs returns a continuation for a subagent step whose run line is stopped when: no later step continues it, STOP.md is absent, and every insert-step item opened from it is addressed or rejected (a rejection is among the decisions the continuation carries). The continuation has the stopped step's kind, target, handoff and queue_item, continues set to the stopped step's id, and a prompt that names the stopped step's report, its committed partial artifacts, and every decision taken on its stop (by id), and tells the step to finish the work from there. A stage condition that the stopped step's partial artifacts happen to satisfy does not count until a continuation of it completes; likewise an insert-step item or a handoff the stopped step's dispatch file names is returned only as that step's continuation (§10.2).

A plan step that wrote STOP.md (a hard stop, §8.2, §8.10, or a producer-cycle stop under policy stop, §10.2) is committed stopped too, but gets no continuation: the new segment's plan step reads the owner's by: owner decision and opens and accepts the insert-step items it implies (an order for a cycle's members, the step that fixes a stuck condition), by plan decisions that cite it.

The stop stays visible throughout: the stopped report, the orchestrator's decision, the run line's stopped status, and the continuation's continues.

#8.4 Deciding in advance

When the setup or plan step can see that the segment will meet a stop-set class (an intake whose change breaks stable contracts will meet breaking-amend on every one of them), the orchestrator may decide the answer once instead of answering the same stop many times. It does so only under decide-and-record, or when an owner fact already gives the answer. It records one decision (type setup or plan, by the step) with would_have_asked: true and the class, and writes predecided[class] with the answer and the decision id; the plan step's write set admits that entry (§7.3). dispatch.mjs puts every predecided answer into every step section (appendix C.2), so a predecided answer added by a plan step reaches the next step. A subagent that meets that class applies the answer, records its own decision with would_have_asked: true, the class, and the predecided decision's id in its evidence, and does not stop. Each such decision is therefore still listed for review.

A predecided breaking-amend answer names the migration mode, coexisting or lockstep (v0.10.0 §3.5), because every bump it covers needs one. A step whose answer names no mode decides it and records that decision with the class breaking-amend (§12.1).

#8.5 Reviewing a step

After the hand-back of a completed step and before committing it, the orchestrator runs routed.mjs ingest --step {step}, so the report's routed items exist, then reads the report and the diff of its write set, and checks:

  • every self_check entry with fail;
  • every artifact the report names exists, and nothing outside the write set changed (the gate repeats this mechanically);
  • every sentence the diff touches is true against the current text of what it cites, and the step did not leave a sentence it read and knew to be false (a step that reports such a sentence as outside its scope gets a rework or a routed item, by a recorded plan decision);
  • the step closed every routed item its dispatch listed (closes);
  • reads_outside is empty, or each entry is recorded (§7.4).

A finding is reworked by resuming the subagent (§8.6), or routed to a later step with routed.mjs open, by a recorded plan decision either way. Every insert-step item the ingest opened is accepted or rejected now, with a plan decision in this step's sidecar (§8.7). Every orchestrator decision belongs to a step whose judgement commit has not been made: this step's, or a plan step's (§10.3); decide.mjs refuses a step that already has one (§10.4).

#8.6 Resume and rework

A resume continues the same subagent, with its context, through the host's message-to-agent capability. dispatch.mjs --resume {step} --reason answer|finding --message-file {file} records it (§6.6) and prints the message to send, which states the answer or finding, the decision id, the report file to write ({step}.r{n}.json), and that the rest of the original prompt still holds.

A step may be resumed for findings (a failed gate or review) at most rework_limit times. The next failure raises gate-twice. Under stop (with gate-twice in the stop set) that is case A. Otherwise the orchestrator records a decision with would_have_asked: true and class gate-twice, commits the step as stopped, and the continuation, a fresh subagent, receives the findings: the decision's why quotes them, and the continuation's ### Continuing lists every report file of the series and the dispatch path (appendix C.2). When the finding is B1 or B5 (no valid report), the stopped commit uses commit.mjs --status stopped --no-report, which skips those two checks, renames the report series {step}.invalid{k}[.r{n}].json and notes it in the run line (§10.7). A continuation that itself reaches gate-twice is a hard stop. Resumes that carry a stop's answer never count against the limit.

When the subagent was lost (the session ended mid-launch), the step is re-dispatched under the same id with dispatch.mjs --redispatch {step} (§8.9), which records a redispatch launch and prints the launch prompt. A redispatch starts a new report series: the step's existing report files are renamed {step}.lost{k}.json and {step}.lost{k}.r{n}.json (k counts redispatches from 1) and stay in the judgement set; the fresh subagent writes {step}.json again; B1, B3, B5 and routed.mjs ingest read only the current series.

#8.7 Inserted steps

An insert-step item comes from a report's routed, from the orchestrator's review, from an intake record's insert rule, or from case C. The orchestrator accepts or rejects it with a plan decision (routed.mjs decide), recorded in the sidecar of the step under review when the item came from its report or review (§8.5), and otherwise in a plan step (§10.3); never between steps. next.mjs returns accepted, unaddressed items as steps before any stage rule, oldest first. The step takes its id at dispatch (§7.2), its dispatch file names the item (queue_item), its invocation carries the item's text (appendix C.2), and commit.mjs marks the item addressed when the step commits as completed; a stopped step leaves it accepted for its continuation. An item may carry after (§6.5): next.mjs returns it only once the named handoff, or every handoff, is executed or skipped, so an insert ordered "before the final align" waits for the handoffs. The orchestrator rejects an item that duplicates a pending handoff (same kind and target), citing it. An accepted item for which no step has been dispatched yet (no dispatch file names it as queue_item) is withdrawn the same way, by a rejected line with a plan decision of its own, recorded where an acceptance would be, when the steps since its acceptance made it moot; once a step has been dispatched for it, it stays accepted, and the step closes it. The orchestrator adds a change-log entry naming the decision.

#8.8 Waiting

The orchestrator waits for the subagent's hand-back; it never polls. With dispatch.wait: hand-back the host notifies the session when the subagent ends; with foreground the launch call itself returns the result. One fallback wake-up of fallback_wakeup_minutes may be set per launch, for a subagent that hangs; it re-reads the state and the subagent's status and sets no further timer. A timed wait shorter than 20 minutes is a defect.

#8.9 Recovering context and resuming after an interruption

Everything needed to continue is on disk. After any context summary, and on every /hsdd-auto that resumes, the orchestrator reads state.mjs, hsdd/auto/plan.md, the last twenty lines of decisions.jsonl and git log --oneline -20 before acting. Before re-entering any handling it reads the step's sidecar and the uncommitted lines of queue.jsonl: a decision or item already present for the same question or text is reused, never minted again; a hsdd/auto/.decide.lock left by a lost subagent is removed. A step that started but has no judgement commit resumes where it stopped:

State on disk Resume by

#8.10 Finishing a segment

When every other condition of the mode holds, next.mjs returns the report step (chapter 9). The orchestrator runs report.mjs, fills the report's prose slots (§10.9), records any last plan decisions, and runs commit.mjs --step {step} --status completed, which runs the final gate before committing. After the commit state.mjs done prints DONE {segment}. The orchestrator ends with one message to the owner: the report's path, the number of steps and decisions, the would_have_asked decisions by id, whether anything stopped, state.mjs done's output, and a reminder that /hsdd-summary re-renders the reading aids, which the run does not drive (v0.10.0 §13.3).

When next.mjs returns stuck, no stage rule can make progress but the done condition fails. The orchestrator starts a plan step (dispatch.mjs --plan), records a decision that names each unmet condition, and either routes it (an accepted insert-step item, or an item for an existing target) or, when no step kind can fix it, writes STOP.md under class shape with the unmet conditions as its question and commits the plan step with --status stopped (§8.3). That is a hard stop (§8.2).

#8.11 Owner messages during a segment

An owner message that arrives while a segment runs is an instruction. After the current step's commits, the orchestrator starts a plan step (dispatch.mjs --plan) and quotes the message in a plan decision that states how it reads it and from which step it applies. A message that changes run.yaml ends the current segment there and opens a new segment of the same mode, whose setup applies the change; the ending plan step is committed with --note "ended: owner message", which state.mjs and next.mjs read as the segment's end (§10.1), and the new segment's report covers the ended one (§10.9). A message that asks the run to stop ends it after that plan step's commits, with no STOP.md; /hsdd-auto resumes it later.

The align condition. The segment's last committed subagent step is an align whose target was, in plan mode, all, and in intake mode every leaf-parent that no step of the segment re-planned, where re-planned means the target of a committed phase-plan or phase-plan-append of the segment (counted from the record's intake step when the segment continues an earlier one, §9.2). An item an align routes whose text equals one closed explained earlier in the segment is not reopened: it is a deferred finding (§10.9), so stage 7 ends after at most one align following the last touch.

Producer-first. Nodes and contracts are ordered so a producer comes before its consumers. Node A precedes node B when B consumes a contract A produces; contract X precedes contract Y when Y's producing node consumes X. Producers and consumers are read from node specs' Produces and Consumes fields and from contract front matter (owner, consumers), where a phase id's node is the id without its trailing numeric segment (acme.backend.billing.2 belongs to acme.backend.billing). Ties keep the order of first mention in the root spec, then in the parent spec. A cycle among the candidates is a shape stop (next.mjs returns stop).

Done for a plan segment (state.mjs done): every stage is done; every contract version above v0, each its own file (v0.10.0 §3.1), is status: stable with phase_ids: final, except a deprecated or retired one (this document exempts v0: an adopted contract, v0.10.0 §6.3, whose phases are not planned until promotion); the registries regenerate clean; every cited ADR, contract, open-question and phase id resolves; no must-address item is open; the ledger validates; and the working tree is clean apart from owner_files. The final gate (F1) checks the same list except the report stage and the clean tree, which only hold after the report step's commit.

The segment's intake record is the newest H/management/*-intake-*.md whose **Request:** line names the segment's request, written by the segment's intake step or, for a segment that continues an earlier one, by that segment's.

A structural class is a shape stop inside the intake step itself (§12.1), so no handoff has run when it fires. A **Promotes:** line is not a stop there: the record orders a promote handoff first, and the promotion stop is hsdd-spec's, raised when that step runs. Collisions with open intake records are resolved by hsdd-intake's own rules (serialize or merge), which are decisions, not stops.

The record's insert rule, when it has one, says which findings add steps (for example: a contract change that alters what a phase implements or replays adds a phase-plan-append and a reconcile on that phase's node, before the align). The intake record stays **Status:** open until hsdd-checkpoint counts its phases done (v0.10.0 §11.5); hsdd-auto never closes it.

#9.3 When the request is a new version of a source

An intake whose request is a new version of a source document also moves citations of the source, and one that supersedes a contract version (a lockstep bump deprecates the old version in the run that drafts the next, v0.10.0 §3.5) moves citations of that version. A coexisting bump moves none: the old version stays live, and each consumer moves in a phase of its own (§12.4). For a new source version the setup step updates sources: the new version becomes normative or informative with its version, and the old one moves to baseline with its own. It also updates the orchestrator_files that name the normative source. Both are recorded decisions. The intake record then routes one citation-touch per artifact that may still cite a superseded string, with when: cites-superseded (§12.2), after the content handoffs, and the touches follow §12.4. No touch moves a contract version in a node header or an ADR's affects: hsdd-reconcile's version ripple writes a confirmed version into the headers and the specs above them, and hsdd-adr adds the new version to affects. So each leaf-parent the change lands on gets a phase-plan-append and a reconcile, and a spec-touch only when its own text changes.

Every script runs from the repository root as node hsdd/scripts/auto/{script}.mjs (from the installed skill's scripts/ before the first copy, §4.3), reads hsdd/auto/run.yaml, and is a pure function of the repository's state and its arguments, except for the files it says it writes and the time it stamps. {"stop": {"class": "shape", "reason": "..."}} A stage rule cannot order its candidates (a producer cycle). The orchestrator handles it in a plan step started with dispatch.mjs --plan: under stop with shape in the stop set it writes STOP.md naming the cycle and commits the step stopped (§8.3); otherwise it decides an order, records it, and opens and accepts one insert-step item per cycle member in that order, which next.mjs then returns before the stage rule.
{"close": {"item": "Q-012", "why": "..."}} An open must-address or consider item targets run or the request path (plan stage 7, intake stage 4). The orchestrator handles it in a plan step (dispatch.mjs --plan --for close): it records the decision and closes the item with routed.mjs close.
{"decide": {"item": "Q-013"}} An insert-step item is still open (a crash before its decision, §8.5). The orchestrator handles it in a plan step (--for decide): it records the decision and runs routed.mjs decide.
{"stuck": ["unmet condition", ...]} No rule can make progress and the done condition fails. The orchestrator handles it in a plan step (§8.10).
{"done": true} The segment's done condition holds.

Selection, in order: waiting; the newest segment's setup step when its entry has no setup commit, then its plan step when it has no plan commit (so a segment opened by an owner's answer can remove STOP.md); blocked; an open insert-step item (decide); a pending continuation (§8.3); accepted, unaddressed insert-step items whose after is satisfied, oldest first (§8.7); the current stage's rule (chapter 9), which yields step, skip, close or stop; then done when the done condition holds, else stuck. An item or a handoff named by the dispatch file of a stopped step that no completed step continues is never returned on its own, only as that step's continuation (§8.3). next.mjs never allocates an id and never writes. Given the same repository state it always returns the same result.

#10.3 dispatch.mjs

text
dispatch.mjs --next [--context-file f.md]
dispatch.mjs --plan --for stop|close|decide|stuck|owner|size|other [--result-file f.json]
dispatch.mjs --resume S07 --reason answer|finding --message-file f.md
dispatch.mjs --redispatch S07

--next runs next.mjs itself and refuses unless the result is step; it allocates the step's id (§7.2), takes rendered_at and head, renders the preamble (appendix B) and the kind's step template (appendix C), and writes hsdd/auto/dispatch/{step}.md with its front matter (§6.6). For a subagent step it prints the dispatch file's path, a blank line, and the launch prompt, the only text the orchestrator passes to the subagent:

text
You are step {step} of an unattended HSDD run. Your complete instructions are
in {dispatch path}. Read the whole file first, then follow it exactly.

The orchestrator never retypes or edits the rendered prompt: the subagent reads it from the file, which is also the audit record. For an orchestrator kind (setup, plan, report) the file's body is empty and only the path is printed.

Size. A dispatch file must come back whole from one file read (Claude Code's Read tool returns at most 25,000 tokens in one call by default, CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS; a longer file comes back as a first page only, and a file over 256 KB is refused), so dispatch.mjs checks the file's size in bytes after every write. At the densest plausible tokenization, about three bytes per token, 64 KiB stays under 22,000 tokens. Above 32 KiB it prints a warning listing each slot's rendered size, largest first. Above 64 KiB it writes nothing and refuses with the same list; a refused --next allocates no id. When {context_lines} is among the largest slots, the orchestrator shortens its context file and runs --next again. Any other refusal of --next or --redispatch is a hard stop (§8.2): the orchestrator records it in a plan step and writes STOP.md with the list. --resume refuses a message that would take the file over the limit, and the orchestrator shortens the message. The fixed text of the preamble and a step section is about 9 KiB; the slots that would otherwise grow with the run are bounded where appendices B and C define them.

Facts come from files. Every fact a template states about the tree is filled by dispatch.mjs from the repository (appendix C.2), each line ending in the path it was read from. The orchestrator may add context through --context-file, but each non-empty line of that file must carry at least one citation token (a repository path containing /, a commit sha of seven or more hex digits, a step id, a decision id, a queue id, or a source citation {cite} §{n}); dispatch.mjs refuses the file and names the line otherwise. Every rendered prompt tells the subagent to check any stated fact it relies on against the file it cites before acting.

--plan starts an orchestrator plan step outside the stage order, for a stop, close or stuck result of next.mjs, an owner message (§8.11), a size refusal (above), or any other decision taken while no step is open: it allocates an id and writes a dispatch file with kind plan and the segment as target, whose body records --for and the next.mjs result in --result-file (an orchestrator step has no read check, so its body may carry them), so a recovery knows what the step was opened for (§8.9). In it the orchestrator records its decisions, may open, accept, reject or close queue items or write STOP.md, and commits it like any other step, stopped when it wrote STOP.md (§8.3).

--resume appends a resume-answer or resume-finding launch, appends ## Resume {n} with the message to the dispatch file's body, and prints the message to send to the subagent; the message names the report file {step}.r{n}.json. --redispatch appends a redispatch launch, adds a ## Redispatch section that lists the files the lost launch changed (git status) and states that earlier ## Resume sections are history and the report goes to {step}.json (§8.6), and prints the launch prompt.

text

For a step, in order:

  1. Resume detection. When HEAD's subject is this step's artifact commit (§6.11) and no judgement commit follows it, skip to step 4. When the index is not empty and HEAD equals the dispatch file's head, a run crashed after staging: unstage everything (git reset) and go on.
  2. Gate per §10.6 for the step's kind and status; on an error, print the findings and exit 1 having committed nothing.
  3. Artifact commit. A stopped step's partial artifacts are committed this way so the tree is clean. With --discard, each named path outside the write set is first restored to HEAD (git checkout --), or removed when untracked, so a step that failed A1 twice can be committed stopped; the run line's note lists the discarded paths, and the orchestrator records a plan decision naming each. With --no-report (a gate-twice raised by B1 or B5, §8.6) the gate skips B1 and B5, the report series is renamed {step}.invalid{k}[.r{n}].json, and the run line's note says no valid report.

  5. Plan. Regenerate plan.md's step log (§6.9).
  6. Judgement commit. Stage the judgement set and commit.
  7. Print both commit shas.

The artifact commit's {summary} is --summary when given, else the report's first notes entry cut to 72 characters, else no summary; for an orchestrator step without --summary it is the segment id.

It refuses to run when a changed path lies outside the write set, the step's report files and sidecar, experiments_dir, the judgement set and the owner files; when the current branch is not the run's; or when the step's report opened an insert-step item still open (§8.5). It never amends, rebases, squashes or pushes.

--skip appends the handoffs.jsonl line (§6.12), regenerates the step log, and makes the skip commit (§6.11). It refuses when the handoff's condition holds or the handoff already has a step or a committed skip line; an uncommitted skip line for the handoff is a crash after the append, and the rerun makes the commit.

#11. The Claude Code Adapter

The skill and its scripts run on any agent host that can launch a subagent with a prompt. The adapter adds what only the host can enforce: reads of out-of-bounds paths and writes to read-only paths, refused before they happen. Without it those rules are instructions in every prompt, as in FT-3, and the gate still catches every write after the fact.

#11.1 What adapter.mjs install writes

adapter.mjs install [--stop-hook] merges into the project's .claude/settings.json, keeping every entry already there, and records each value it added in hsdd/auto/adapter.json (schema: appendix A.10) so adapter.mjs uninstall removes exactly those and nothing else.

Permission deny rules. For each out_of_bounds path, a Read(...) rule; for each read_only path, an Edit(...) rule. The host's rule syntax is gitignore-style, and the script translates the owner's path forms:

Owner writes Rule path
An absolute path /a/b //a/b/** (a double slash is the filesystem root; a single leading slash would anchor to the project)
A home path ~/a/b ~/a/b/**
A project path a/b /a/b/** (anchored to the project root, so it does not match a/b at any depth)

A glob the owner wrote is kept as written, with /** appended when it does not end in **, so a directory glob also denies the files under it; adapter.mjs check tries a file under such a path (§11.3). Write(...) rules are not written: the host does not consult them, and Edit(...) rules govern every file-writing tool. A Read deny also blocks edits of the same path. The host applies Read denies to its search tools on a best-effort basis and to recognized shell file commands (cat, head, tail, sed, tee, redirections), but not to arbitrary subprocesses; the hook below and an operating-system sandbox close what remains. Deny rules apply to the subagents the session launches.

A Bash PreToolUse hook. One entry under hooks.PreToolUse with matcher Bash and the command node "${CLAUDE_PROJECT_DIR}/hsdd/scripts/auto/hook-bash.mjs". The hook reads the event JSON on stdin and takes tool_input.command. It blocks the call, with exit code 2 and the reason on stderr (which the host returns to the agent), when:

  1. the command text names an out_of_bounds path in its owner form, its absolute form or its ~ form, or a path a glob in the list matches;
  2. the command writes to a read_only path by redirection or a file command (>, >>, tee, cp, mv, rm, sed -i, touch);
  3. the event carries agent_id (the call comes from a subagent) and the command changes git state: git with commit, add, rm, mv, reset, checkout, switch, restore, stash, rebase, merge, cherry-pick, revert, push, tag with an argument, branch with any argument other than --list, -a, -r, -v, -vv and --show-current, or update-ref.

Otherwise it exits 0 with no output. The hook matches text, so it cannot see a path a program computes at run time; the gate and the sandbox are the backstops. The host documents agent_id as present when the hook fires inside a subagent, and its examples omit it for the main session; the orchestrator in any case changes git state only through commit.mjs and state.mjs open-segment, whose command text names no git subcommand, so rule 3 never matches them.

A step agent type. .claude/agents/hsdd-auto-step.md, with front matter name: hsdd-auto-step, a description, model from run.yaml's models.step when set, and a tools allowlist of the file, search, shell and skill tools a step needs, with the agent-launching tool left out and also named in disallowedTools: the host otherwise lets a subagent start subagents of its own, three levels deep, and a step must not. The orchestrator launches every step with this agent type.

An optional SubagentStop hook. With --stop-hook, an entry under hooks.SubagentStop runs hook-subagent-stop.mjs when a subagent ends. It reads the subagent's own transcript path from the event's agent_transcript_path (transcript_path is the main session's), finds the dispatch path in the subagent's first message (the launch prompt of §10.3), and when the dispatch file's report is missing or fails appendix A.4, it blocks the stop with the reason "Write your report to {path} before ending"; when the latest report's read_check differs from the dispatch file's last line (B5), it blocks with "Read {dispatch path} to its end, then correct your report". The host then gives the subagent that reason as its next instruction. Any other subagent, or a missing or unreadable transcript, exits 0.

#11.2 Isolating memory

Agent hosts keep per-project memory and transcripts outside the repository, where an out-of-bounds rule must name them. Two ways, in order of strength:

  • Launch the orchestrating session with CLAUDE_CONFIG_DIR set, in the shell that starts the host, to a directory used only for the run. User settings, transcripts and per-project memory then live under that directory, and other projects' memory is outside the session's tree. The variable cannot be set from project settings.
  • Otherwise list the memory paths in out_of_bounds (~/.claude*/projects/*/memory), which installs read denies and the hook rule.

#11.3 Checking the adapter

adapter.mjs check verifies that every rule the configuration implies is in .claude/settings.json, that the hook commands point at the current copy, and runs hook-bash.mjs on sample events: a cat of each out-of-bounds path in each of its forms must exit 2; ls of the project root must exit 0; git commit -m x with an agent_id must exit 2 and without one exit 0; git branch new-name with an agent_id must exit 2. Every setup step runs the check and records a failure as a setup decision: fix it, or proceed with the rule as an instruction only.

#11.4 The /goal condition

Claude Code's /goal keeps a session working until a condition holds, judged after each turn by a small model that sees the conversation but cannot read files or run commands. The condition must therefore be something the orchestrator prints. state.mjs goal prints, for the current segment:

#12.2 hsdd-intake: the handoff block

The intake record's ## Routing section may carry, after its prose, one fenced block with the info string hsdd-handoffs holding JSON (appendix A.7):

markdown
```hsdd-handoffs
{
  "version": 1,
  "handoffs": [
    { "id": "H1", "kind": "adr-update", "skill": "hsdd-adr", "target": "ADR-003",
      "prompt": "Amend ADR-003 for ...", "when": null, "after": [] },
    { "id": "H7a", "kind": "citation-touch", "skill": "hsdd-contract", "target": "topic-model",
      "prompt": "Touch topic-model@v1 for ...", "when": "cites-superseded", "after": ["H1"] }
  ],
  "insert_rule": "A contract change that alters what an unshipped phase implements or replays adds phase-plan-append and reconcile steps on that phase's node, before the final align."
}
```

  • id: H{n} with an optional lower-case letter for a family (H7a).

  • kind: a subagent step kind of §7.1 except intake; skill the one §7.1 gives it; target in the form §6.5 gives for that kind:

    Kind Skill Target
    mid-level-spec, graft, promote, spec-touch hsdd-spec a node id
    adr, adr-update hsdd-adr an ADR id
    contract, contract-touch hsdd-contract a contract slug (its id; {id}.v{n} names one later version, v0.10.0 §3.1)
    citation-touch by the file: hsdd-spec, hsdd-adr or hsdd-contract a node id, ADR id or contract slug
    phase-plan, phase-plan-append hsdd-phase-plan a leaf-parent's node id
    reconcile, align hsdd-reconcile node ids, comma-separated, or all

  • prompt: the exact handoff prompt, as the record's prose gives it.

  • when: null (always dispatched) or cites-superseded.

  • after: handoff ids that must be executed or skipped first. An empty list means "after the previous handoff in the list"; the first handoff waits on nothing.

  • insert_rule: optional, plain text; the orchestrator applies it (§9.2).

cites-superseded holds when any of the target's files contains a superseded string. The superseded strings are: for every baseline source in run.yaml, its path, and its version tied to its citation name, {cite} {version} or, when the version does not start with v, {cite} v{version}, with whitespace between the two, the name not inside a longer word and the version followed by neither a letter, digit, _ or - nor a . and a digit (a bare version string is no citation: a version 1 would match every number); and for every contract id whose current version, the highest any file of that id holds (v0.10.0 §3.1), is v{n} with n above 0, each {id}@v{k} with k below n that is superseded, followed by a character that is not a letter, digit, _ or -, or by the end of the text. A lower version with a file of its own is superseded only when that file is deprecated or retired: under coexisting it stays stable while it has a live consumer (v0.10.0 §3.5), and a citation of it is live. A lower version with no file of its own lives only as history inside a later file (a bump in place, before 0.10.2) and is superseded. A version's own files (its contract file, schema and fixtures) describe it, so {id}@v{k} in them is no superseded string. The target's files are: for a contract id, every version's file with its schema and fixtures (H/contract/{slug}.md, H/contract/fixture/{slug}/** and H/contract/schema/{slug}.schema.json for the first version, {slug}.v{n} in place of {slug} for a later one); for {id}.v{n}, that version's files; for an ADR, its file; for a node, its spec file. The match is textual and counts history too: a target whose only old-version mentions are history is still dispatched, and its touch keeps them (§12.4). next.mjs evaluates the condition when the handoff comes up, not when the record is written.

The block is optional, and its absence keeps a record conformant (v0.10.0 §15.3). hsdd-intake writes it whenever it runs with --unattended, and may write it otherwise. The skill gains a section Handoff block carrying this subsection: the example, the field rules, the kind table and the meaning of cites-superseded, so a step needs no other text to write it. A structural record's block has an empty handoffs list, since its handoffs are the owner's decision; the continuation after the answer (§8.3) re-classifies the request, rewrites ## Routing with the handoffs and the block, and logs the change in ## Change log. The prose stays authoritative for people; the block must say the same thing: the prose quotes each handoff's prompt verbatim, in the block's order, and hsdd-intake's quality gates gain the line "the handoff block, when present, lists the same handoffs as the prose, in the same order, with the same prompts".

#12.3 hsdd-reconcile: align mode

hsdd-reconcile gains one operation, align, as a numbered step after its step 13 and a mode paragraph; step 13's sweep of resolved open questions and its trigger words are unchanged. Align runs standalone, with no pending section present, like the steps the skill's step 2 names. It is invoked as /hsdd-reconcile align {node ids or all} after {what changed} and, for each named node's plan text:

  1. moves every live citation of a contract version that is superseded (§12.2: deprecated or retired, or with no file of its own) to the current version, by §12.4's rule, in unshipped phases only and never in a node header's Produces or Consumes line; a citation of an earlier version that stays live beside the new one (coexisting) stays, and align routes one consider item to the node, naming the new version, since moving a consumer is that node's planning, never align's;
  2. re-derives each phase gate's contract and guarantee arguments against the validation artifacts of the version the phase cites, where the gate names them;
  3. checks that every phase id named in a contract's produced_by, consumers or delivery text exists, and that every phase Scope that cites an intake record cites one that exists;
  4. records every finding it cannot fix within citations and gate arguments (a Scope that is now wrong, a phase that no longer fits) as a routed item for the owning skill, never rewriting a phase's scope itself.

It drains nothing and flips nothing unless the invocation also names those steps. Its quality gates gain "every change align made is a citation or a gate argument".

#12.4 Citation touches when a version moves

When a source document moves to a new version, or a contract version is superseded, every artifact that cites the old version is touched once, by its owning skill (hsdd-contract, hsdd-adr, hsdd-spec), under this rule, invoked as citation touch {file}: move its citations to the current versions, which those three skills gain as a paragraph Citation touch. A contract version is superseded as §12.2 says: its file is deprecated or retired (lockstep deprecates it in the run that drafts the next version, v0.10.0 §3.5), or it has no file of its own (a bump in place, before 0.10.2). A coexisting version stays stable while it has a live consumer, and each consumer moves to the new version in a phase of its own.

  • A live citation of a superseded version moves to the current one: an unshipped phase's boundary or delivery line, a guarantee citation, a fixture header comment, a node's Sources entry for a source document, any sentence that states what holds now.
  • Never move a contract version in a node header's Produces or Consumes line, or in a copy of that line above the node (a parent's embedded summary, child-node table or DAG, the root's contract matrix): hsdd-reconcile's version ripple writes those, keeping every version the node's phases name (v0.10.0 §3.5). Never edit an ADR's affects: hsdd-adr adds the new version there.
  • A copy of a child node's header lines in its parent's spec (the parent's embedded summary of the child, child-node table or DAG) is the parent's text: the citation touch on the parent moves the source citations in it, matching the child's own Sources entry when that has already moved, and a citation touch on the child changes only the child's own file.
  • An earlier contract version that is neither deprecated nor retired stays live beside the new one (coexisting): leave every citation of it, and route one consider item, naming the new version, to the node whose plan would move to it (the node of the citing phase, or the producer or consumer the citing sentence is about), so that node's own planning decides when it moves.
  • A shipped phase (one whose verification doc is on the spec repo's main line, the conventions' **Main line:**, main when absent, v0.10.0 §14.2) is history in full: nothing in it moves, and the touch reports each such reference as kept.
  • Historical text keeps the version it describes: a dated amendment entry, a migration note, a "Corrected" paragraph, an account of what an earlier version did.
  • When a moved citation sits in a sentence the new version makes false, restate the sentence to match the cited artifact's current text, and record one decision per sentence: what it said, what it says now, which part of the new version it follows. That is a compatible wording change in the touched file.
  • Never change the touched artifact's own declarations, guarantees, cases or fixture behavior in a citation touch. When keeping a sentence true would need that, leave it, route it as a finding, and name the step it needs.
  • Classify the touch against the touched artifact's own versioning rules (it normally stays at its version) and record that as one decision.
  • Report how many citations moved and how many were kept, as history or as a live earlier version.

The final gate's F2 lists what still names a superseded version, so the report can say that each remaining reference was read and is history.

#12.5 What stays deferred

HSDD's templates use an em dash as an empty-cell token and in some headings. A project that bans the character writes the replacement forms of §7.6, which §15.3 admits into the frozen formats because every bundled parser already reads them. What stays deferred is making the templates themselves configurable: they keep the em dash, and a project that bans it relies on the prompt to say otherwise.

#13. Templates and Prompts

#13.1 What a subagent receives

The launch prompt (§10.3) points at the dispatch file. The dispatch file's body is the rendered preamble followed by the rendered step section. The subagent therefore starts with no context but the file, which is the isolation HSDD wants for every skill run, and the orchestrator spends no output on restating it. The file is at most 64 KiB, so one read returns it whole (§10.3), and it ends with the read check (§6.6).

#13.2 Slots

A slot is {name} where name is lower-case letters and underscores. A literal brace pair in a template is written doubled: {{name}} renders as {name}. Text in braces that contains anything else (a space, a comma, a capital) is never a slot and renders as written. Slots are filled only from run.yaml, the segment entry, the step and the repository, by the tables in appendices B and C, and dispatch.mjs fails on a slot it cannot fill. A fill is itself rendered once before insertion, so a fill that names a slot ({decide_command} names {step}) comes out filled; a slot in the fill's own output is left as written.

#13.3 The preamble

templates/preamble.md (appendix B) is the same for every step of a segment. It carries, in this order: who the subagent is and what one step is; the segment's context; the inputs and the out-of-bounds paths; the owner facts and preferences; the decision policy; the stop set and the segment's stop policy; how the policy applies to a step subagent; the rules of the run (write set, no git, no interactive companion skills, experiments, prose rules, citation forms, owner files, read-only paths); and the report's shape, as a JSON skeleton.

#13.4 The step section

templates/steps/{kind}.md (appendix C) has a common header, generated blocks, and the kind's own instructions:

  1. Header: step id, skill and its arguments (with --unattended {step}), target, report path, the decide command, the write set.
  2. Invocation: an intake handoff's prompt verbatim, or the kind's default.
  3. Facts (generated): the current state of every artifact the step reads or must keep consistent, each line ending in the file it was read from.
  4. Routed to this step (generated): the open queue items that match the step (§6.5), by id; the report must close each.
  5. Predecided answers (generated). They appear here and not in the preamble, so the preamble stays the same for a segment's steps when a plan step adds one.
  6. Continuing (generated, for a continuation only): the stopped step, its report, its committed partial artifacts, and the decisions taken on its stop.
  7. Context from the orchestrator (optional, from --context-file, every line cited).
  8. What to do: the kind's instructions, including that the skill's own templates are the format, so the step never needs a sibling artifact for format (§7.4).
  9. Done when: the conditions, ending with the gate command the subagent may run itself.

#13.5 Changing templates

Templates are part of the skill. A template change ships in a skill release with a VERSION change and a CHANGELOG entry. Each dispatch file records the template and the skill version that rendered it, so an audit compares like with like.

#16.3 Rejected

  • A Claude Code plugin as the package. It gives tool-level enforcement but ties the method to one host; the adapter gives the same enforcement as an optional layer.
  • Agents typing timestamps, with validation afterwards. FT-3 shows the failure is not malice but convenience; a check after the fact cannot recover the true time.
  • Ids minted at commit time. A decision's id is needed before its commit: in a resume message, a STOP.md, a predecided answer, a queue event.
  • The orchestrator writing prompts freehand. It costs the most output tokens of anything the orchestrator does and is where wrong facts entered.
  • One global stop policy per run. The owner's tolerance changes with the work: FT-3's owner wanted stops for the first plan and none for the intake.

#C.3 Instructions per kind

root-spec (hsdd-spec, root). Default invocation: "Decompose the system into its root node, {target}, from the normative sources and the owner facts." What to do: follow hsdd-spec at the root. Write the root spec and one spec file per child. Name every contract on an edge by id; propose ADRs for cross-cutting decisions; mint open questions in the node that owns them. Seed conventions.md with the coding method, ordering policy and teams lines the owner facts give. List every source in ## Sources with the authority run.yaml gives it, deciding and recording one where it is absent, and mark each informative source with the skill's phrase "informative only, not decomposed". Done when: the root spec and every child's file exist; conventions.md exists; every edge names its contract id.

mid-level-spec (hsdd-spec). Default invocation: "Decompose {target}." What to do: apply hsdd-spec's rule for when to stop recursing; either decompose into children with one file each, or mark the node leaf-parent and say why. When the result changes what the parent's embedded summary or DAG says, route an insert-step for a spec-touch on the parent. Done when: the node's Kind is final and every child it names has a file.

graft (hsdd-spec, graft mode). Default invocation: "Graft under {target} the child this step's routed item or handoff names: {reason}." What to do: follow graft mode (v0.10.0 §11.4): the new child takes the next slug; the parent's child summaries and DAG gain it; contracts it consumes from siblings are left to the child's phase plan's request entries. Done when: the child's file exists and the parent names it.

promote (hsdd-spec, promotion mode). Default invocation: "Promote {target} from as-built to governed: {reason}." What to do: follow promotion mode (v0.10.0 §6.4) with the node's ## Observed surface as a primary source beside the request; the confirmation the mode asks for is a promotion stop unless predecided. Its v0 contracts stay at v0 unless the promotion redesigns one (hsdd-contract's versioning policy). Done when: the node's Adopted line reads promoted, ## Observed surface is kept, and its spec reads as a governed node's.

spec-touch (hsdd-spec). Default invocation: "Touch {target}: {reason}." What to do: follow the skill's Touch paragraph (§12.1): change only what the invocation and the routed items name. Do not edit the node's ## Phase Plan. Done when: every routed item is closed and nothing else in the file changed.

adr (hsdd-adr). Default invocation: "Materialize {target} as {proposing_spec} proposes it." What to do: write the ADR accepted under the decision policy, citing your acceptance decision's id in its ## Context (§12.1); run an experiment when the decision rests on a runtime fact; add Governed by to every node it affects and governed_by to every contract (§12.1); regenerate the registries, copying the generator from hsdd-contract verbatim when it is missing. Done when: the ADR file exists and every affects target names it.

adr-update (hsdd-adr). Default invocation: "Update {target}: {reason}." What to do: add an entry under ## Amendments (§12.1) or supersede, as the invocation says; never rewrite the decision's history. Done when: the change is in place and every affects target is consistent with it.

contract (hsdd-contract). Default invocation: "Author {target_id}@{target_version}." What to do: write every front-matter field (status: draft, phase_ids: provisional, governed_by naming the ADRs the facts list), the Interface, Guarantees with ids G{n}, ## Versioning with its Breaking: line (§12.1), and ## Validation with the schema and fixtures written now; prove executable fixtures with an experiment where the toolchain can run them; regenerate the registries. Done when: the file and its validation paths exist.

contract-touch (hsdd-contract). Default invocation: "Touch {target}: {reason}." What to do: classify the change against the contract's own ## Versioning. A breaking change to a stable contract is a breaking-amend stop unless a predecided answer covers it; then apply the answer; under compatibility: frozen or at v0 it is a run-stop candidate whatever the predecided answers say (§8.2). The answer names the migration mode, coexisting or lockstep; when it names none, decide the mode and record it (§12.1). Update the fixtures of the version you change; a new version writes its own schema and fixtures beside the old ones. Done when: the change is in place, classified and recorded.

citation-touch (hsdd-contract, hsdd-adr or hsdd-spec). Default invocation: "Citation touch {target_file}: move its citations to the current versions." What to do: apply §12.4's citation-touch rule exactly: never move a contract version in a node header's Produces or Consumes line, a copy of it above the node, or an ADR's affects; leave every citation of a live earlier version (coexisting) and route a consider item for it; move the source citations in this file's copies of a child node's lines (an embedded summary, child-node table or DAG), matching the child's own Sources entry when that has already moved. On a child node, change only its own file: the copy of its lines in the parent's spec is the parent's touch's (§12.4). Report the counts moved and kept in notes. Done when: no citation the rule moves names a superseded string, and every sentence that restates another artifact is true against its current text.

phase-plan (hsdd-phase-plan). Default invocation: "Plan the phases of {target}." What to do: follow the skill's phase record and plan document templates exactly; they are the format. Read the node's own spec, its contracts, its ADRs and conventions.md. Do not open another node's ## Phase Plan or pending section, for format or anything else (v0.10.0 §8.3). Every gate of a producing phase replays the contracts it produces. Emit confirm, amend and request entries in the pending section. A gap in a consumed contract that changes which phases exist is a shape stop. Done when: the plan has its summary table, dependency graph and pending section.

phase-plan-append (hsdd-phase-plan, append mode). Default invocation: "Append phases to {target} per {record}." What to do: as phase-plan, plus append mode's rules (v0.10.0 §11.3): never renumber; never rewrite a shipped phase (one with a verification doc on the conventions' **Main line:**, main when absent, v0.10.0 §14.2); rewrite an unshipped phase in place only when the invocation says so (§12.1); every phase rewritten or appended cites in its Scope the intake record, or in a plan segment the insert-step item's id; when there is a record, the change request's own path (the facts name it, never the record's) joins the node's Sources with the sections that govern it; the pending section gets a new emission date line. Done when: as phase-plan, and every phase the invocation names is rewritten or explained.

reconcile (hsdd-reconcile). Default invocation: "Reconcile {target}." What to do: follow the skill's steps in order. A collision is a collision stop; an amend or request answer that breaks a consumer of a stable contract is a breaking-amend stop unless predecided; for a draft contract, and for every other request, you decide. Hand nothing to hsdd-adr or hsdd-contract yourself: route an insert-step (§12.1). Done when: every pending section in the tree is stamped as reconciled (the skill drains the whole tree; the target names the plans this step was ordered for) and the flips the skill allows are made.

align (hsdd-reconcile, align mode). Default invocation: "Align {target} after {reason}." What to do: §12.3. Route every finding beyond citations and gate arguments to its owning skill. Done when: the named plans cite no superseded version, except history.

intake (hsdd-intake). Default invocation: "Route {request} ({authority}) into the tree." What to do: follow hsdd-intake: read every open intake record first, locate the landing, classify, and write the record before any handoff, with the handoff block of §12.2. A structural class is a shape stop. A landing on an as-built node puts a promote handoff first (§9.2). For a new version of a source, order the handoffs: content handoffs producer-first (ADRs and contracts before the specs and plans that consume them); then one citation-touch per artifact that may still cite a superseded string (when: cites-superseded); then, for each affected leaf-parent, a phase-plan-append and a reconcile (a spec-touch only for a change to the node's own text, never for the contract version in its header, which the reconcile writes). Order no align: the segment's align stage follows the handoffs (§9.2). State an insert rule. Read the earlier would_upstream decisions in the facts against the request, and record in notes which it adopts, contradicts or leaves open. Write no spec, contract or ADR. Done when: the record exists with every header field, its prose routing and its handoff block, and the two agree.
